## 分解定位（这轮差距 1.34x 从哪来）

| 冷启动（首跑） | 43 ms | 31 ms | 池 256 MB 后从 5ms 差缩到部分缓解 |

per-shape（warm）：

| shape | rust | cpp | 备注 |
|---|---|---|---|

| Conv 32→64 k1x1 ×3 | 1.3 | 1.5 | 反超 |

| Mul ×13 | 2.7→**1.4** | 1.4 | 本轮已修（见下） |
| Add ×23 | 1.7 | 1.1 | 1.5x |
| Resize ×6 | 1.2 | 1.2 | 持平 |
| Relu ×20 | 0.9 | 0.5 | 1.8x（fork 开销占比） |

## 本轮顺手修的两个问题

1. **池上限 64 MB→256 MB**：det 的 concat/中间张量 95 MB 级，64 MB
   上限把最大块全部挤出池（冷跑差 5ms 的主因）。
2. **binary_op 分配路径漏接 AVX2**（Mul 13 个节点全标量）：
   快路径 1（单元素）、2（run）、同形三条全部接上；对拍发现并修正了
   向量 run 的双重偏移 bug（bsrc 已偏移又 add(ib)）。修后 Mul 2.7→1.4ms。

## 5. 并发调参（v4，2026-09-23：线程数/并发扫描 + K=2 定位）

工具：`tools/sweep_parallel.py`（档位轮转防漂移；跨设备可直接复跑）。
线程数经 `QPPOCR_THREADS`（rust）/ `LEAN_THREADS`（cpp）注入——
本轮把线程数管道接通（`par::set_threads` + `EngineBuilder::threads` +
env，对齐 C++ `resolve_threads`：显式请求不设 16 上限）。

### 单进程延迟 vs 线程数（Σ7 图 ms，3 轮旋转）

| t | 4 | 6 | 8 | 10 | 12 | 14 | 16 |
|---|---|---|---|---|---|---|---|
| rust | 626 | 591 | 576 | 561 | 561 | **558** | 560 |
| cpp | 604 | — | 609 | — | **555** | — | 567 |

t≥10 后平坦（±1%），**默认 16（= min(逻辑核, 16)）不动**；4P+12E 的
异构性在这条曲线上不构成可利用的信号（14 vs 16 在噪声内）。

### 吞吐 vs (K, t)（img/s，中位；粗体=该引擎峰值）

| K	 | 2 | 3 | 4 | 6 | 8 | 16 |
|---|---|---|---|---|---|---|
| 1 | | | 12.9 | | 12.4 | 12.4 |
| 2 | | | | | 17.4 / 21.5 | 16.4 / 19.4 |
| 3 | | | 19.9 | 21.2 / **24.5** | **21.7** / 23.1 | |
| 4 | | | 22.2 / **24.3** | **22.8** / 23.0 | | |
| 6 | | 25.0 / — | 22.2 / 24.5 | | | |
| 8 | 20.5 / 21.4 | 20.4 | | | | |

（格式 rust / cpp；空白未测。）两引擎形状一致：**吞吐峰在总线程
≈ 1.2~1.5× 逻辑核**——rust 峰值 K=6×t=3 = 25.0 img/s，cpp 峰值
K=3×t=6 ≈ K=4×t=4 ≈ 24.4；K=8 双双回落。经验规则：
`t ≈ max(2, round(cores × 1.25 / K))`。

### K=2 差距定位（v3 的 1.142x → 机制拆解）

| 对照 | 结果 | 结论 |
|---|---|---|
| 池唤醒：condvar vs 信号量（V2 移植 C++ 原版） | 信号量 K=2 慢 ~7%（853 vs 798ms@t8），已回退 | **不是唤醒机制**；广播一次 syscall 优于计数累积 |
| join：纯自旋 vs 自旋+让出（V1） | 无差（797.2 vs 797.9） | **不是自旋**；保留自适应版（病态场景更稳） |
| **t=1（池静止）K=2** | **rust 1578 vs cpp 1458 = 1.083x** | **8% 底差在串行段**：内存足迹/缓存争用（det 双缓冲、arena String 键），与池无关 |
| 等线程数 K=1 | 持平（±5%） | 差距**只在多进程争用下出现** |

即：K=2（1.26x@t8）≈ 8% 串行段争用底差 × 池放大。修法在 executor
的内存布局（arena 键内化、det 缓冲复用），属独立优化项。**吞吐部署
的实操建议：K≥4 × 低线程**——rust 在 K=6×t=3 即追平 cpp 峰值
（25.0 vs 24.5 img/s），K=2 恰是两引擎相对差距最大的工作点。

### 跨设备检测能力边界

- **单进程延迟**：`available_parallelism()` + 16 上限就是最优
  （曲线 10~16 平坦），无需检测 P/E 核——本机实测检测了也不改变默认。
- **吞吐部署**：最优 (K, t) 取决于**兄弟进程**，库内不可见，本质是
  部署参数而非检测问题。给出旋钮（`EngineBuilder::threads` /
  `QPPOCR_THREADS` / CLI `--threads`）+ 上述经验规则；
  `tools/sweep_parallel.py` 在目标设备直接复跑即可标定。

## 7. CLI 批量 `--workers`（v6，2026-09-23：进程扇出，对齐 C++ proc_pool）

背景：C++ CLI 多图模式自动起 worker **进程**（`auto_workers` +
`proc_pool.hpp`）——100 图 5.7 s vs 我们顺序 14.0 s。两条实现路线的
实测（tiny 档、simdpaddleocr-dataset 100 图）：

| 方案 | 100 图 | 说明 |
|---|---|---|
| 顺序单进程×16 线程 | 14.0 s | 引擎耗时 × 100 |
| 进程内 8 线程共享引擎 | 7.4 s | fork_mu 串行化并发 fork：串行段可重叠，并行算子排队 |
| 进程内 + fork 宽度收窄（16/8） | 15.3 s | **错误方向**：fork_mu 下收窄=总并行度降到 2；且 gemm 分轴随线程数变，**破坏位级一致**（路径选择本身进位，见 gemm.rs），已回退 |
| **进程扇出 8×2（采用）** | **5.9 s** | 独立小池真并发；连续切块按序拼接=输入序 |

- 扇出 vs 顺序（同 t=2）：**0/100 图差异**——机制完全忠实；与 t=16
  顺序比有 1/100 位级差（gemm 分轴随线程数，引擎固有性质，C++
  `--threads` 同款），聚合评分不变（864/1036、CER 2.81% 均同）。
- `auto_workers` 启发式照搬 C++（头部探测平均 MP：≥1.5 MP cap 2、
  小图 cap 8、核数减半）；未搬内存预算——单机 16 核 cap 8 已约束。
- 小批量：7 图 497 vs C++ 479 ms、2 图 316 vs 291 ms（平手量级，
  扇出的 spawn 税与 C++ 相互抵消）。
- **产品侧（API 用户）另有进程内选项**：共享 `Engine` 多线程并发
  `run`（`fork_mu` 保证安全）零 spawn、单份权重，适合交互场景的
  小批量——这是 C++ 架构给不了的（其池并发调用会挂死）。

## 剩余差距的已知构成（v2 历史，v3 换池后大部分消化）

- ~~多线程扩展 1.86x vs 2.07x~~ → 换池解决（本轮）。
- depthwise（g32/g48/g64）在引擎上下文曾 1.4x，micro-bench 持平——
  「单次执行 vs 反复热跑」的上下文差异，怀疑是指令缓存/分支预测器
  冷启动，C++ 单一大编译单元在此占优。候选手段：conv 分支按
  group/shape 特化内联。
- Add/Relu 等小算子的 fork 次数（56 次/图）固定开销：池的 fork 代价
  与 C++ 同量级（~97us@16t），此项两边对等。
- K=2 并发 1.142x（见 §3）。
