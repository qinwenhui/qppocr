# 迁移可行性对拍（C++ ↔ Rust）

**这是一个内部迁移辅助工具，不是这个 crate 的公开基准套件。**

## 它们是什么

把参考实现里的 GEMM 微内核**逐句搬到 Rust**，两边用同样的编译选项跑同一组形状，
用来回答一个具体问题：

> **同一套算法，在 Rust 里会不会更慢？**

答案（2026-09 实测）：**不会，反而略快。**

### 来源

这两个内核来自我们自己的 **C++ 参考实现**（一个手写 SIMD 的 PP-OCRv6 推理引擎，
已有三年基准与调参历史）。移植评估时把它们抽出来做了对拍——
`bench.cpp` / `bench.rs` 是同一套 4×4 AVX2+FMA 分块 GEMM，
`mem.cpp` / `mem.rs` 是同一套张量分配模式。

**这是移植前的先导实验，用来决定"要不要做 qppocr"**，结论是值得做。

## 实测结果

### GEMM（交错 5 轮取最好值，`-O3 -mavx2 -mfma` / `-O -C target-feature=+avx2,+fma`）

| shape | C++ | Rust | Rust/C++ |
|---|---|---|---|
| M=3136 N=64 K=576 | 3.240 ms | 3.111 ms | 0.960x |
| M=1024 N=256 K=256 | 1.860 ms | 1.716 ms | 0.923x |
| M=512 N=256 K=576 | 2.083 ms | 1.982 ms | 0.952x |
| M=64 N=64 K=64 | 0.007 ms | 0.006 ms | 0.857x |
| **合计** | 7.190 ms | **6.815 ms** | **0.948x** |

**四个形状的校验和逐位相同** —— 移植是数值忠实的（FMA 顺序一致），
不是"算得快是因为算错了"。

### 内存（交错 4 轮）

| | 墙钟（最好值） | 峰值工作集 |
|---|---|---|
| C++ | 1060.6 ms | 90.5 MB |
| Rust | 1003.6 ms | 89.5 MB |

墙钟 0.946x，峰值内存基本相同。**没有内存损失**——两边都是同一套系统分配器，
`Vec` 和 `std::vector` 同为 (ptr, len, cap)，Rust 也没有 GC。

## 怎么跑

```bash
# C++
g++ -O3 -mavx2 -mfma -o bench_cpp bench.cpp
g++ -O2 -o mem_cpp mem.cpp -lpsapi

# Rust
rustc -O -C target-feature=+avx2,+fma -o bench_rust bench.rs
rustc -O -o mem_rust mem.rs
```

★ **必须交错跑。** 在一台单次跑分波动可达 ±27% 的机器上，
"先跑完 C++ 再跑 Rust"量到的是机器漂移不是语言差异——
第一版就是这么跑的，得出过"Rust 反而快 25%"的荒谬结论。
每个二进制跑 5 轮、交替顺序、取每轮的最好值。

## 注意事项

- `mem.rs` 里 `PROCESS_MEMORY_COUNTERS` 的字段顺序是 `cb(u32)` + `PageFaultCount(u32)`
  之后才是 7 个 `SIZE_T`。**写成 `cb` + 一个 `usize` 会整个读串一位**，
  峰值读成 `0.0` —— 读得到数但是错的。这个坑在第一版里踩过。
- 这两个程序**不需要模型、不需要语料**，任何机器上都能跑。
  这是它们能留在这里的原因：**公开仓库里不该有依赖第三方语料的测试**。
