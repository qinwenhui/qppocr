# GPU 健康门禁与判别探针

这台 M4（MacBook Air, Mac16,12, AGXG16G, macOS 26.3.1）上，GPU 有一种**静默的致瘸模式**：
算力完好、DRAM 空闲、没有任何报错，但**整条访存通路的带宽掉到 1/50~1/65，且只有重启能恢复**。
在瘸掉的机器上测任何性能数字都是假数。这一套工具的作用是：**先证明机器是健康的，再谈优化**。

> 这些探针原本在 `/tmp`，被一次重启清空过。现在源码入仓，重启后 `./build.sh` 三秒重建。

> ## ⚡ 根因已定、已修、已验证（2026-10-08 22:43）
>
> **不是驱动缺陷，是我们自己的 bug**：Metal 后端把**整个会话共用一块 arena**（Vulkan 是每计划一块
> 私有 arena），而 `Layout` 每次 build 从 `cursor=0` 重新 bump → **后建计划的静态区压掉先前计划的
> 参数块**；命中计划缓存时又**一个字节都不重传** → shader 读到垃圾参数 → 巨循环 → 挂死 → 打瘸。
> 修法是派发前按需**重放**被冲掉的静态块（`ensure_statics`），健康路径零成本。
> `./fixcheck.sh` **5/5 全过**（10 图/一进程/一会话 **0.52 s**，同形态当初是 120 s 超时 + 打瘸）。
> **细节、证据、验证口径见下面「✅✅ 根因已定位」一节。** 下面那些「未证实」「已否掉」的
> 机制假设均已被它取代 —— 留着是为了记录排除过程，**别当结论用**。

## 一分钟上手

```sh
cd bench/gpuhealth
./build.sh          # 编译全部探针（约 3 秒）
./health.sh         # 体检：健康 / 存疑 / 已瘸，退出码 0/1/2
```

**每次重启后的第一件事是 `./baseline.sh <标签>`**，不是直接开测。它把四组基线（带宽 / **纯 ALU** /
尺寸曲线 / 四条访存路径）一次抓全，存到 `logs/baseline_<标签>.txt`。理由见下面「方法论教训」一节：
我此前判定"算力正常"时拿的是**瘸态下**的数字去比一个**假设**的降频倍数，没有真基线。

`health.sh` 的判据**只有实测带宽**，不看计数器：

| 实测 blit 带宽 | 判定 | 动作 |
|---|---|---|
| ≥ 60 GB/s | 健康（正常 83~95） | 可以测性能 |
| 10~60 GB/s | 存疑 | 复跑确认；别出数字 |
| < 10 GB/s | 已瘸 | **停手重启** |

`recoveryCount != 0` 直接判瘸（有过 GPU 页故障）。但 **`recoveryCount == 0` 不代表健康** ——
实测打脸过一次：计数器干净地回到 0、一份 `gpuEvent` 都没有、内核日志一条 GPU 报错都没有，
而苹果自己的 blit 只有 0.25 GB/s。**唯一可靠的判据是实测带宽。**

## 📏 带宽上限：120 GB/s 是怎么来的、我们实际到多少（2026-10-08）

这一节回答两个问题：**官方那个 120 是什么数**、**我们真能到多少**。所有性能结论里凡是
「离带宽上限还差多少」，分母都该取这里实测出来的数，**不是 120**。

**120 GB/s 的来历**：Apple 对基础版 M4 的规格 = LPDDR5X-**7500** MT/s × **128** bit 位宽
÷ 8 = 7500e6 × 16 B/s = **120 GB/s**。它是**内存总线的理论峰值**，且 **CPU 与 GPU 共用同一条**。
所以：任何单边负载都到不了 120；读写各半的拷贝类负载，两边加起来也不该超过 120。

**本机实测（`./membw`，512 MB，5 轮取最快，均按实际 DRAM 流量记）**：

| 路径 | 流量口径 | 实测 | 占 120 |
|---|---|---|---|
| CPU memcpy（随机源） | 2×bytes | ~86 GB/s | 72% |
| CPU memcpy（常量源，对照） | 2×bytes | ~85 GB/s | 71% |
| CPU 只读（逐 8 字节求和） | 1×bytes | ~68 GB/s | 57% |
| CPU 只写（`memset`） | 1×bytes | ~68~73 GB/s | 57~61% |
| **GPU blit 拷贝**（Shared→Shared） | 2×bytes | ~92 GB/s | 77% |
| **GPU blit 拷贝**（Private→Private） | 2×bytes | ~93~95 GB/s | 78~80% |

**结论**：这台机器拷贝类的**真实上限约 93 GB/s（≈规格的 78%）**，CPU 与 GPU **同量级**
（CPU/GPU ≈ 0.9）。做「离带宽上限还有多远」这类判断时，**分母用 93，不要用 120**；
要用 120 时，先按 78% 打个折。

> 尺寸扫描（32 MB ~ 512 MB）显示**带宽与块大小基本无关**，192 MB 以上稳定在 ~86 GB/s。
> 但**必须预热**：冷态首跑会低 15~40%（32 MB 行曾量到 41 GB/s），极易被误读成「块越小越慢」。
> `membw` 的扫描和 `gpuhealth` 的 CPU 行现在都带预热，别删。

### ⚠️ 曾经的假数：`gpuhealth.m` 报的 CPU 135~147 GB/s（已修）

这个数**长期出现在日志里**（`baseline_reboot1.txt` 的 147.05、`decay_1008_213520.txt` 整列
135~147），**比规格峰值 120 还高 22%——它本身就是自证的假数**。成因是**编译器，不是硬件**：

clang `-O2` 做常量传播，看见上面刚 `memset(s, 1, bytes)`，就把 `memcpy(t, s, bytes)`
**改写成了 `memset(t, 1, bytes)`**。反汇编可验：原 `gpuhealth` 二进制里 `bl _memcpy`
**一次都没有**，只有 `bl _memset` 且 `w1=1, w2=0x10000000`。于是那行干的是**纯写**，
而公式仍按拷贝记 `2.0*bytes`（读+写）→ **凭空虚高正好 2 倍**。

对账闭合：`membw` 的同尺寸 `memset` 纯写得 **73.49 GB/s**，2 × 73.49 = **147**，
正是那个假数。修法是在 `memcpy` 前加一条空内联汇编
（`__asm__ __volatile__("" : "+r"(s), "+r"(t) : : "memory")`）抹掉值信息，
修后 CPU 行回到 **~82 GB/s**，`CPU/GPU` 从假的 2 倍变成真实的 **0.9 倍**。

**一度误判为「Apple 透明内存压缩虚高」**（源是单字节常量，本机 `vm_stat` 也确实有压缩活动）。
**已否掉**：同场对照里「随机源 vs 常量源」读数一致（84.98 vs 85.37），压缩没帮任何忙。
真正的元凶自始至终是编译器。想复现/验证这个教训，`./cpumin` 有四组同进程对照
（新鲜页 / 预触碰 / 随机源 / 空转拉频 / 先跑 GPU），**四组全是 ~87** —— 环境变量全部排除。

> 附带影响：`decay_1008_213520.txt` 的「blit」列当年是**按所有 GB/s 取最大**抓的，
> 所以每行抓到的都是 CPU 那行、不是 blit（该文件顶部已加警示）。结论不受影响 ——
> 真瘸时 CPU 与 GPU 两条一起崩，取最大也还是低值。脚本已改为只抓 `GPU（` 开头那行。

## 判别实验 `stress.m`

```sh
./stress inbounds 30    # 严格界内的重型访存（大 pool + 大量小 dispatch，全部界内，Private）
./stress churn    30    # 大块 Private buffer 反复分配/释放（同时活着的始终很少）
./stress manybuf  30    # **大量不同尺寸的 Shared buffer 同时活着** —— 引擎计划集的真实形态
./stress mixed    30    # 以上三者各 1/3
./stress idle     30    # 对照：什么都不做，只等同样长的时间
```

每种模式都是「测健康 → 施压 N 秒 → 复测健康」，健康测法与 `gpuhealth` 一致，数字可直接比。
前测只要 <10 GB/s 就直接返回 3（机器本来就瘸，本次对比无意义）。

**`manybuf` 为什么必须单独有**（2026-10-08 补的盲区）：`inbounds` 只用 2 块 buffer；`churn`
虽然分配了 20,064 次，但每块都是**分配后立刻释放**，所以「同时活着」的缓冲区始终只有 1~2 块。
而引擎的真实形态完全不是这样——它为**每个输入形状**建一份计划、每份计划一整块 arena，
旧计划还持有旧 arena 不释放（计划缓存预算 384 MB），所以同时活着十几块、尺寸从 1.4 MB 到
137.8 MB 不等，而且是 `StorageModeShared`（CPU 直接写 `contents()`），不是 `Private`。
这条轴前两个模式**根本没覆盖**，却恰好是引擎的行为。

**怎么读结果**（重启后立刻跑，一次只跑一个模式，跑完看后测带宽）：

- `inbounds` 后掉到 1.x GB/s → 只要**界内大量访存**就能打瘸，与越界无关 → 得回头查 arena 布局/地址模式
- `churn` 后掉到 1.x GB/s → 是**大块显存分配/释放的搅动**打瘸的 → 改 arena 策略（预分配 + 复用，别翻倍增长）
- `manybuf` 后掉到 1.x GB/s → 是**多块不同尺寸 Shared arena 同时活着**打瘸的 → 收窄计划集 / 限制同时驻留的 arena
- 三个都健康 → 需要引擎里更具体的行为（越界 / 特定地址模式）→ 下一步拿引擎本身二分
- `idle` 也掉 → 与我们的负载无关，是系统里别的东西周期性打瘸的 → 查远控/驱动

> ⚠️ **跑一次瘸一次就重启一次。** 已用对照实验证过：给挂住的进程发 SIGTERM、进程干净退出后等 8 秒，
> blit 仍是 1.40 GB/s —— **客户端进程死了，已提交的 GPU 工作照样跑**，`MTLCommandBuffer` 没有取消 API。
> 所以不要靠反复跑基准做二分；先用 `idle` 对照把嫌疑范围压到最小。

## 已知结论（2026-10-08 实测）

> **这一节测的是「瘸态长什么样」（诊断特征），依然有效、依然是最快认出瘸态的依据。**
> 至于**为什么**会瘸 —— 现已查明是我们的共享 arena 覆盖 bug（见顶部与「✅✅ 根因已定位」）。

**病在 GPU 共用的那段访存通路（地址翻译 / L2-SLC / 显存接口），不在算力、不在调度、不在任何客户端进程。**

| 测量 | 结果 | 排除了什么 |
|---|---|---|
| 空 command buffer | 0.03 ms | 提交/驱动延迟 |
| 尺寸 4/16/64/256 MB | 1.19 / 23.8 / 95.9 / 591 ms（线性） | 固定开销；确认是带宽被限 |
| DMA 读+写 / DMA 纯写 / SM 读+写 / SM 纯写 | 1.93 / 1.38 / 1.81 / 1.68 GB/s | 「有 shader 死在 SM 占住 GPU」——纯写不碰 SM 一样慢 |
| 同时刻 CPU memcpy | 145 GB/s | 「有东西抢内存」 |
| 纯 ALU | 瘸态 690.79 / **健康 3083.99** GFLOP/s（同口径 iters=4096） | ❌ **不是「只有访存坏了」** —— 见下 |
| 4 MB 小拷贝 | 瘸态 7 GB/s（比大拷贝快 5 倍） | 缓存路径比 DRAM 路径受损轻得多（健康态反而更慢，见下） |

**⚠️ 「算力路径是好的」这个旧结论已被健康基线推翻。** 同口径 iters=4096：
**3083.99 / 690.79 = 4.46×** —— 瘸态下**算力也掉了 4.5 倍**，只是访存掉得更狠（72×）。
两种损伤量级不同（4.5× vs 72×）说明**不是单一的整块降频**；4.46 很接近 1470/330 ≈ 4.45，
像是核心被压在最低频档，访存那 72× 是**叠加在上面**的另一层损伤。

**尺寸曲线的方向在两种状态下是反的**（别再用它推「页数 vs 字节数」）：

| | 4 MB | 16 MB | 64 MB | 256 MB |
|---|---|---|---|---|
| 健康 | 29.33 | 58.15 | 82.09 | 93.79 GB/s |
| 瘸态 | ~6.7 | ~1.34 | ~1.33 | ~0.87 GB/s |

健康态**小传输更慢**，纯粹是每次提交 ~0.169 ms 的固定成本没被摊薄（不是页数问题）。
瘸态反过来，说明「4 MB 还有 7 GB/s」**只是缓存没被打瘸**，DRAM 路径其实已经均匀崩了。
**我此前据 4 MB 快 5 倍推出的「代价随页数走 → MMU/缺页」是建立在混淆项上的，撤回。**

**内存压力已排除**（2026-10-08 实测）：`Pages stored in compressor` = 0，
`Compressions/Decompressions` = 0/0，`Swapins/Swapouts/Pageouts` = 0/0/0，
系统内存空闲率 92%，最大常驻进程 WindowServer 379 MB。不是被别的进程挤出去的。

一并排除（都实测过）：电池/低电量降频（`pmset -g batt` 报"电池供电"是**过期缓存**，以 `ioreg`
的 `ExternalConnected` 为准）；温控降频（`pmset -g therm` 无告警）；向日葵采集占住 GPU
（全线程空闲在 `mach_msg`/`kevent`，零个 Metal 帧）。

**爆炸半径远超"基准测不准"**：瘸掉之后 WindowServer 会被看门狗判死，导致全屏黑掉、机器没法用
（`evidence/` 里三次 `WindowServer-*.ips` + `userspace_watchdog_timeout.spin` + `forceReset-*.diag`）。
排查黑屏先看 `/Library/Logs/DiagnosticReports/WindowServer-*.ips`，别只看 `gpuEvent`。

## 2026-10-08 判别实验结果：**四条「负载形态」轴全部否掉**

重启后（健康 94.8 GB/s）按顺序各压 30 秒，每步都复测带宽：

| 实验 | 负载 | 后测带宽 | 结论 |
|---|---|---|---|
| `idle` | 什么都不做 30 秒 | 72 GB/s | 时间本身不会掉 |
| `inbounds` | **257,792 条 dispatch** + 589 blit，全界内、随机地址、随机尺寸、每条后 barrier | 94 GB/s | **不是"dispatch 太多/形状太多/随机地址"** |
| `churn` | **20,064 次**大块（1~128 MB）Private buffer 分配 + fill + 释放 | 94 GB/s | **不是"大块显存分配/释放搅动"** |
| `manybuf` | **24 块不同尺寸 Shared buffer 同时活着**（12 种 1~138 MB，共 634 MB）+ 30,048 次界内访存 | 71.99 → **73.62** GB/s | **不是"多块 Shared arena 同时驻留"** |

`inbounds` 的 dispatch 数是整轮 100 图引擎基准（~15,400 条）的 **17 倍**，仍然健康。
`manybuf` 补掉了「引擎外」最后一个盲区（`Private` 与 `Shared` 两种存储模式现在都覆盖了）。
**所以凶手不在负载的量、也不在负载的形态**——剩下的可能只有两类：
**引擎 dispatch 的具体内容（真·越界 / 特定 offset）**，或**系统里别的东西**。

## 2026-10-08 衰减曲线实验：**是台阶，不是斜坡**；变量是「批大小」，**不是**并发进程数

`decay.sh 10 12` 在刚重启的健康机器上跑：

| 轮次 | 负载 | 引擎 | 复测带宽 | `Alloc system memory` |
|---|---|---|---|---|
| 00 | 无 | — | **95.24 GB/s** | 0.77 GB |
| 01 | 10 张 / **5 个 worker 进程** | 180 s 未返回，被掐断 | **0.77 GB/s** | **2.06 GB** |

**一批就打瘸了，没有爬坡过程。** 此前那条「随累积 GPU 工作量单调衰减
（95.6→82.6→72.0→0.5）」的假设**已被这次受控测量证伪**。

### 三个臂：变量是图数，不是进程数

| 臂 | 总图数 | 进程数 | 每进程 | 结果 |
|---|---|---|---|---|
| A | **2** | 2 | 1 张 | ✅ 健康 81.62 GB/s |
| B | **10** | 2 | 5 张 | ❌ 打瘸 0.92 GB/s |
| C | **10** | 5 | 2 张 | ❌ 打瘸 0.77 GB/s |

**B 与 C 总图数相同、进程数不同，两个都瘸；A 只是图少就健康。**

> **⚠️ 一处自我更正（2026-10-08 22:02）。** 我先据 C 得出「凶手是并发 worker 进程数」，
> **这个结论是错的，已撤回。** 当时 A 与 C 之间**同时**变了两个量（进程数 2→5、每进程工作量
> 1→2 张），我从那个混淆的对照上外推了。B 这一臂（10 张 / 2 进程）正是为拆开这个混淆而跑的
> `worker_sweep.sh` 第 1 步，**它把我否掉了** —— 2 个进程照样打瘸。这正是该实验该干的事。

### 顺带否掉「驱动内存膨胀」

| 场景 | `Alloc system memory` |
|---|---|
| 起始（无负载） | 0.80 GB |
| 5 进程瘸 | 2.06 GB |
| **2 进程瘸** | **0.98 GB** |

2 进程瘸的时候只占 0.98 GB —— 内存占用只是**随进程数变多的伴生现象**，不是致瘸原因。

### 早期指纹：退化在批的前几张就开始了

10 图那批里**先跑完的几张就已经慢了**：142~178 ms/张，而健康的 2 图批是 **93 ms/张**。
所以退化不是「跑满 10 张才崩」，阈值大概在 2~10 张之间，不高。

### `--workers 0` 在这台 10 核机上 = 5 个并发进程（仍成立，但不是致瘸变量）

`auto_workers()`（`crates/qppocr-cli/src/main.rs:318`）：核数 10 → `min(10,16)/2 = 5`，小图 cap 8 → 取 5
（子进程内部还被再包一层 `--workers 1 --threads 2`）。这个事实本身值得记，**但它不是凶手**。

### 定量关联：驱动侧 GPU 内存

| 并发 worker | `Alloc system memory` |
|---|---|
| 2（健康） | 0.77 GB |
| 5（打瘸前后） | 2.06 → 2.23 GB |

每个 worker 为**每个输入形状**分配一块大 `StorageModeShared` arena 且旧计划不释放；5 个进程
= 5 份独立 GPU 地址空间、每份数百个同时存活的分配。**「并发多进程 × 大量存活分配」是现在的首要假设。**

### 一处自我更正：「竞争已排除」要收窄

此前写过「竞争无法解释 70 倍崩塌」，依据是**单个**竞争进程压满 GPU 时 blit 只掉 22%（94.9→74.3）。
那个对照只变了**占空**，没变**地址空间多样性**（2 块 buffer、只多 1 个进程）。它排除的是
**「GPU 时间被抢走」**，**不能**排除多进程地址翻译 / MMU 压力。
正确表述：**纯占空竞争已排除，多进程地址空间压力未排除。**

### 立即规避手段

**`QPPOCR_METAL_NO_ARENA=1` 是目前唯一实测有效的回避手段**（见下一节的判定结果，
10 张已实测健康）。但它是**诊断开关、不是修复**：代价是每份计划各拿一块私有 buffer、
每次 build 全量上传。

**默认路径仍然一批 10 张必瘸** —— Metal 后端在这台机器上**还不能处理真实批量**。
这是可用性问题，比"性能慢"严重得多。

### ✅✅ 根因已定位、已修、已验证（2026-10-08 22:43）——**这条为准，下面两条机制假设都作废**

上面「第 N≥2 次 build 就坏」找对了**变量**，但机制假设指错了**读到的垃圾是什么**。
真凶是**共享 arena 里「后建计划的静态区压掉先前计划的参数块」+ 命中缓存时不重传**。

**Metal 后端独有的一处偏离**：`MetalSession` 用**一块会话级共享 arena**
（`arena: Mutex<Option<Arc<Mutex<Arena>>>`, `session.rs:107`），所有计划都往里装；
而 **Vulkan 给每个 `Plan` 一块私有 `Arena`**（`crates/qppocr-gpu/src/vulkan/session.rs:79`）——
所以这条 bug 只可能在 Metal 路径上出现，也解释了「只有 Metal 会打瘸」。

**机制（链条完整、每一步都有代码或实测支撑）**：

1. `Layout::alloc`（`crates/qppocr-gpu/src/plan.rs:1769`）与 `Layout::alloc_static`
   （`plan.rs:1807`）**共用一个 `cursor`**，而 `Layout::new()` 每次 build 都把它归零；
2. 于是静态区偏移**随形状漂移**，后一次 build 的静态块落在**先前计划的参数块**上；
3. `plan_for` 命中缓存时**直接返回、一个字节都不重传**（`session.rs` 的 `plan_for` 路径）；
4. 派发时 shader 从参数块读到**别的计划的参数** → 迭代次数/步长变成垃圾 → 巨循环 → 挂死；
5. **参数块是形状相关的**（编码 stride/shape），所以**不存在任何布局技巧能让两份计划共用
   同一偏移** —— 唯一的修法是**派发前把字节重放回去**。`plan.rs:1800-1806` 那段注释只保护了
   **单次 build 之内**（「静态区只在装载期写一次」隐含「一块 arena 只服务一份计划」），
   共享 arena 下这个前提根本不成立。

**判决性证据（纯主机侧、零派发，所以不受 GPU 状态影响）**：对 rec 的形状序列建若干份计划，
**7/9 份的静态区被后续 build 冲掉**：

| 形状 | 在位块数 | 在位字节 |
|---|---|---|
| `[4,3,48,256]` | 13/154 | 9.08/13.47 MB |
| `[8,3,48,192]` | 19/154 | — |
| `[1,3,48,384]` | 79/154 | — |
| `[1,3,48,1024]` | 82/154 | — |

过一遍 `ensure_statics` 之后 **9/9 全部复原**。而 **det 那两个形状恰好重合**（321/321、0 份被冲）
—— 所以**确定性触发者是 rec**，正对上「图 2 的 rec 形状命中图 1 建的计划」。

**修法**（`crates/qppocr-metal/src/backend/session.rs`）：`MetalPlan` 记住①自己那块 arena 的
`Arc`、②静态区的**写入清单** `statics: Vec<(u32, Arc<Vec<u32>>)>`、③它的标识视图 `recipe`；
`run` 在**每次派发前**调 `ensure_statics(&plan)`，按 `Arena::blobs` 这个账本做**块级跳过**、
只重放已被冲掉的部分。清单里两个上传列表都是 `Arc<Vec<u32>>`，所以记住配方只花几次引用计数
（参数是 KB 量级），**健康路径零成本**：单图每份计划建完立刻跑，`blobs == recipe` 直接早返回、0 次重放。

**验证：`bench/gpuhealth/fixcheck.sh` 5/5 全过**（判据跑之前先定好，避免事后解释）：

### ❌ 已作废的机制假设（曾标「最强」，**未证实且已推翻**）：依赖「新 buffer 是干净的」

两次健康配置的共同点是**每次 build 都用全新 buffer**（arm A 每进程 1 张；
NO_ARENA 每计划一块）。Metal 不保证 `new_buffer` 清零，但新分配的缓冲区实际常常是干净的；
而复用后它装的是**上一张图的残留**。若计划里有任何区域 **build 从不写、shader 却要读**
（padding / 假定 0 的累加初值 / 填充区），就会：新 buffer → 正常；复用 buffer → 读到垃圾
→ 巨循环 → 挂死。这正好对上仓库自己记的故障形态（`plan.rs:1804`：「消费方读到垃圾参数
→ 巨循环 → GPU 挂死设备丢失」），也正好解释「第一张好、第二张坏」。

⚠️ 上一个假设（**跨计划别名竞态**）已被代码审计**否掉**，别再沿用：`MetalSession::run`
入口取 `run_lock`（`session.rs:593`）且 `build_plan` 在该锁内（`session.rs:615`）；提交是同步的
（`device.rs:39-41` `commit()`+`wait_until_completed()`）；Metal 没实现 `run_deferred`；
进程内多图是顺序 for 循环（`main.rs:523-536`），并未行靠 spawn 子进程（`main.rs:557-588`）；
`--threads` 是 CPU 内核池，与图片并行无关。**不存在重叠访问。**

（审计顺带查出一个**将来**会变成真竞态的点：`arena` 的 Mutex 不覆盖真正写字节的循环
`session.rs:413-435`，`probe` 调 `build_plan` 不取 `run_lock`（`session.rs:234-236`）——
今天只因调用点在装载期才安全。等补上异步 `run_deferred`（`session.rs:126` 标着 P4）就会出事。）

### ⚠️ 曾经的「跨计划别名」假设：**方向对了，措辞错了**（别整条丢掉）

`alloc_static`（`plan.rs:1807`）**每次 build 都从 cursor=0 重新 bump**，所以不同形状的静态
权重落在**同一批偏移**上；而复用模式下一个会话**只有一块** arena，所有 `MetalPlan` 都指向它。
**这一段是对的，而且是真凶的一半。** 我先前把它整条判成「已否掉」是**过了**——当时只否掉了
其中的**并发**成分，不是这件事本身：

- **确实被否掉的是「竞态」**：`run_lock` 的审计（见上一节）证明了**不存在重叠访问**；
- **没被否掉、后来被证实的是「覆盖」**：**根本不需要任何并发** —— 顺序的两次 build 就够了。
  后建的计划写自己的静态区时，直接压掉先前计划**已经装好、且下次派发还要读**的参数块
  （见上面的根因节）。这是**数据生命周期**问题，不是线程安全问题。

所以「别名」这个词本身没错（两块逻辑数据占了同一段物理偏移），错的是我把它和**竞态**绑在一起，
一否竞态就顺手把整个假设丢了。**教训：否掉一个假设的某个成分时，别把整个假设一起判死。**

（跳过集本身自洽、不会误跳——这条仍然成立：`(偏移, 字数, Arc地址)` 三元组能唯一确定内容
（Arc 出自会话级 `repack_cache`，按权重名缓存、永驻，`plan.rs:1950-1959`），且跨形状时
`a.blobs` 会被写回更新。跳过逻辑没错，**错的是「跳过之外没人重传」**。）

```
21:53:53  Wake   Wake from Deep Idle [CDNVA] : due to MTP.DOCK.CHANNELS.AP0.IRQ … RTP.keyboard/UserActivity
```

`boottime` 全程 `1791466088` 不变 → 是**真·唤醒**，不是偷偷重启（`wake_probe.sh` 每轮都打
boottime 就是为了防这个误读；**一旦变了，那次测试作废，不是"失败"**）。

> ⚠️ **别指望"让它自己空闲睡眠"**：Claude Code 跑后台任务时会挂 `caffeinate -i -t 300`
> （父进程是 `claude` 本身），它挡的是**空闲睡眠**。必须用 `sudo pmset sleepnow` **强制**睡眠，
> 强制睡眠无视这些断言。`pmset -g assertions` 里还能看到 `powerd` 和第三方（如 `EsDevMonitor_CCB`）
> 的 `PreventUserIdleSystemSleep`，同理。

**结论：瘸掉之后没有任何免重启的恢复手段。** 已试过并全部否掉：① SIGTERM 杀客户端进程
（进程干净退出后 8 秒复测仍 1.40 GB/s）；② 睡眠/唤醒（本节）；③ 等它自己好（盯 5 分钟，
平在 0.20–0.28 GB/s）。**这条现在是穷尽枚举后的结论，不是推测** —— 所以每次 GPU 实验都要
按「一次挂死 = 一次重启」来预算。

## 「引擎挂死」的真相：**是减速，不是死锁**（已实测坐实）

2026-10-08 重启后：单图（独立进程）健康跑完 63.92 ms、跑完健康 92 GB/s
→ 10 图 `--workers 0` bench 卡住 336 秒没返回
→ **趁它卡着测**：GPU blit 只有 1.32 GB/s（CPU/GPU = 104×），`recoveryCount = 0`，无 fault 报告
→ 而那条 blit **跑完了**，只是慢 70 倍 → **命令缓冲区不是"永不完成"，是龟速执行**
→ 杀掉进程后再测单图：**能跑完**，total 1176 ms（**18×** 慢），11 行文本与置信度**与健康态逐字一致**
→ 杀进程无效：SIGTERM 干净退出后 GPU 仍是 1.5~1.7 GB/s

**所以顺序是：引擎的 GPU 工作把访存通路打瘸 → 之后每一轮都慢 18~70 倍 → 看起来就是"挂死"。**
先前的"引擎提交了一条永不结束的 dispatch 把 GPU 钉死"和"引擎自身能干掉整台机器"两个归因**都已撤回**。

有意思的细节：引擎只慢 18×，而苹果自己的 256 MB blit 慢 56× —— 与"越大的传输越惨（4 MB 小拷贝仍有 7 GB/s）"吻合。

## 免 root 的瘸态检测器：活动监视器里的 WindowServer

**健康时 WindowServer 的 GPU 占用约 8%；瘸了之后是 80–100%（多数时候 100%）。**
打开活动监视器 → 点 GPU 列排序看一眼就行，不用跑探针、不用 sudo。

窗口里的因果方向**是结果不是原因**（已实测裁决）：访存通路掉到 1/70 之后，WindowServer 合成
同一帧的代价涨了几十倍，它只能把 GPU 占满才勉强画出桌面。用户在自己的机器上先观察到了这个
现象，我们据此做了下面这个对照实验把它证掉。

### 对照实验：「竞争 / 抢占」能否解释 70 倍崩塌？——**不能**

| 条件 | 256 MB blit |
|---|---|
| 无竞争 | **94.94 GB/s** |
| 另一个进程正在把 GPU 打满（`stress inbounds 30`） | **74.32 / 78.14 GB/s** |
| 竞争结束后 | 93.24 GB/s |

即使有另一个进程在狂压 GPU，blit 也只掉 **22%**。所以**竞争解释不了 1.3 GB/s**，瘸态是真实退化，
不是"GPU 时间被抢走"。复现命令：

```sh
cd bench/gpuhealth
./stress inbounds 30 > logs/contention_bg.log 2>&1 &
sleep 4 && ./gpuhealth && ./gpuhealth
wait
./gpuhealth
```

## 定位工具：`QPPOCR_METAL_CHUNK`

默认整块提交时，全部 dispatch 先在 CPU 侧编完、才进唯一那次 `waitUntilCompleted`，
所以日志只能告诉你"计划建好了"，**无法告诉你卡在哪条**。两个新环境变量：

```sh
# 每 8 条 dispatch 一块，逐块 commit+wait，每块墙钟立刻刷到 stderr
QPPOCR_METAL_CHUNK=8 QPPOCR_METAL_CHUNK_BAIL=1500 \
  target/release/qppocr <imgs> --tier tiny --device metal --workers 0
```

- `QPPOCR_METAL_CHUNK=N` —— 切块大小。`N=1` 就是逐条 dispatch 计时。
- `QPPOCR_METAL_CHUNK_BAIL=ms` —— **刹车**：任一块等待超过这个数就认定"刚被这一块打瘸"，
  打印凶手内核区间后 `exit(97)`，不再提交后续 dispatch。
  两个好处：① 一分钟内拿到凶手区间，不用等挂死；② 少给已瘸的 GPU 灌工作量（瘸了之后每次提交都在拖 WindowServer）。

不设变量时走原来的整块路径，逐位不变。实测输出形如：

```
[chunk] run#0 输入 [1, 3, 960, 864]（真实行 1）→ 154 条 dispatch，切块 64，整块 43053054 word
[chunk] run#0    0..64   等待   184.51 ms  ["n_entry" → "n_conv8"]
[chunk] run#0   64..128  等待   129.88 ms  ["n_conv8" → "n_conv_dw"]
[chunk] run#0  128..154  等待   182.70 ms  ["n_conv8" → "n_exit"]
```

## 方法论教训：**没有健康基线的数字不能用来下结论**

我曾写下「纯 ALU ≥690 GFLOP/s → 所以算力路径是好的、整块 GPU 没被降频」。**这个推论不成立**：

- 那个 690 是**在瘸态下测的** —— 我**从来没有采过健康态的 ALU 数字**；
- 我拿它去比的是一个**假设**的降频倍数（1/68 → 只该有 ~60 GFLOP/s），而不是一次真实测量；
- M4 十核 GPU 的 fp32 峰值量级是 ~4 TFLOP/s，这个 6 链 FMA 循环正常应到 **2~3 TFLOP/s**。
  690 只有峰值的约 **17%** —— 完全可能它**本身就已经被压过了**。

所以 `../baseline.sh` 才是每次重启后的第一步。**任何时候想说"这个部分是好的"，先拿出它健康时的数字。**

## 硬件节流计数器的存在性已被确认，但读数需要 root

`ioreg -r -c IOAccelerator -l` 里有一组此前没注意过的字段：

- `"IOReportSubGroupName" = "GPU Throttler Counters"`，含
  `Throttle Counter HWPI / DPE / Misc / IVDM / Total` 以及 `IVDM: Min/Max Active Throttle Percent`
- `PPM Target as % of Max GPU Power`（PPM = 电源/性能管理）
- `GPU Power Zone Filter 0..4` / `GPU Power Filter`、`GPU Discrete Power Zone Engaged`、
  `AFR Power Controller States`、`GPU Energy`
- 完整 `PerformanceStatistics`（`recoveryCount` / `lastRecoveryTime` 也在这里）

**⚠️ 但 ioreg 只暴露 IOReport 的「图例」（通道 id + 单位标志），不暴露数值。**
例如 `4311875585,"Throttle Counter Total"` 里的 4311875585 是**单位标志**，不是计数。
要读数值必须用 root 权限的 `powermetrics`：

```sh
sudo powermetrics -n 1 -i 1000 --samplers gpu_power | grep -iE "freq|resid|power|busy|throttle"
```

这组数据能区分两件至今没分清的事：

- **GPU 活跃频率顶在最大（~1470 MHz）** → 不是电源管理降频，问题在驱动 / MMU / 内存记账
- **频率明显低于最大、或 Throttle 计数在涨** → 是**锁存的电源管理降频**，
  那 `pmset sleepnow`（睡眠/唤醒）这类「重新走一遍电源状态机」的手段**有机会**免重启恢复
