# 激活流量不是约束 —— fp16 激活这条改造路被判死（2026-10-10）

**问题**（用户）：把激活也改成 fp16，改造大吗？能有比较大的提升吗？

**答**：改造**很大**（不是翻开关），收益**约 0~7%**。实验见下。

---

## 27.1 为什么会有这个问题

竞品 `sdcb/SimdPaddleOCR` 是**整条流水线 fp16**（激活走 `device const half4*`，
DRAM 流量减半），而我们是**只有权重 fp16**（`QPPOCR_METAL_F16W`，激活与累加
仍是 f32）。他们 det 快我们 1.38×，fp16 激活是候选解释之一。

而激活恰恰是卷积访存的大头——最小流量式

```
4·(cin·m + co·m)     ← 激活（读输入 + 写输出）
4·cin·co·taps        ← 权重
```

1×1 层 m 有几千、cin/co 才几百 ⇒ **激活占绝对多数**。所以「激活减半」看着
像一笔大钱。

## 27.2 改造量：大

`crates/qppocr-gpu/src/nhwc.rs:9-14` 当初**明确写了为什么故意不做**：

> 权重可以按 fp16 存，**激活与累加仍是 f32**……**这不是「加一个 f16 张量
> 类型」**：`DType`、解析器、模型文件、CPU 后端全都不动

真做要动：

| 面 | 量 |
|---|---|
| `DType` 引用点 | **13 个文件**（executor / onnx 解析 / planner / vulkan / metal …） |
| 内核 | 21 个里 **16 个**直接读写 `device float4*` 激活，全要 half4 变体 |
| 布局 | `nhwc_words` 假定 1 word = 1 个 f32 元素 ⇒ 段大小/偏移/静态 arena 全变 |
| 边界 | entry/exit 的 f32↔f16 转换、CPU 回退路径、全部正确性测试 |

## 27.3 收益：先算，再量 —— 预判是「不大」

`bottleneck_map_20261008.md` §10.3 早就把 conv8 的达成率量出来了：

| | 实测 | 峰值 | 利用率 |
|---|---|---|---|
| conv8 算力 | 437 GFLOPS | 3.34 T | **13.1%** |
| conv8 带宽 | 10.5 GB/s | ~78 GB/s | **11.2%** |

**两个屋顶都空着 8/9**，当时的判语是「**这是延迟特征，不是吞吐特征**」。
fp16 减的是字节，不治延迟。旁证：`p_m8n4` 把每 FMA 的权重字节减半 → **收益 0**。

## 27.4 量的办法：补上激活那一侧的对照

`conv_probe.rs` 的变体表里**本来只有权重那一侧**、激活侧没有对照：

| 变体 | 掩掉什么 | 保留什么 |
|---|---|---|
| `p_base` | 无（控制组） | — |
| `p_wsmall` | **权重**地址 → 1 KB 窗口 | 条数、地址算术 |
| `p_fmaonly` | **全部 load** | 只有 FMA |
| **`p_ismall`（本次新增）** | **激活读地址** → 1 KB 窗口 | 条数、地址算术、**权重一字不改** |

`p_ismall` 由 `probe_p_base.metal` **逐字节拷贝**而来，只改内核名 + 引入
`amask` + 把 `d[ib + px*cin4v + ci4]` 换成 `d[ib + ((px*cin4v + ci4) & amask)]`。
（`p_base` 与 `p_wsmall` 的 diff 已核：那边也只有 `& 0x3Fu` 一处。）

**诚实边界**：只掩**读侧**（热循环里 `taps × cin4v` 次装载），**不掩输出写出**。
故意如此——把输出也掩进 1 KB 会让所有 warp 砸同一条 L1 line，那是写出争用的
人造瓶颈，会把数**往上**带。所以读数应理解成**下界**。

复现：`cargo test --release -p qppocr-metal conv8_variant_scan -- --nocapture`

## 27.5 结果：10 个生产形状，`p_base / p_ismall` = 1.00 ~ 1.35×

| 形状 | p_base ms | **p_ismall ms** | **base/ismall** | base/wsmall | base/fmaonly |
|---|---:|---:|---:|---:|---:|
| rec ctc head 216x1 c120→18710 k1 | 3.571 | 3.557 | **1.00×** | 4.49× | 9.95× |
| rec 48x544 c32→32 k3 | 0.464 | 0.438 | **1.06×** | 1.04× | 2.44× |
| rec 24x272 c64→64 k3 | 0.493 | 0.479 | **1.03×** | 1.05× | 2.37× |
| **det 480x432 c32→32 k3** | 3.387 | 3.176 | **1.07×** | 1.06× | 2.55× |
| rec 6x68 c256→256 k1 | 0.079 | 0.079 | **1.00×** | 1.01× | 2.19× |
| det 34x60 c192→384 k1 | 0.413 | 0.363 | **1.14×** | 1.53× | 3.36× |
| det 34x60 c384→192 k1 | 0.451 | 0.335 | **1.35×** | 1.60× | 3.79× |
| det 17x30 c384→768 k1 | 0.353 | 0.335 | **1.05×** | 1.30× | 2.97× |
| rec 6x208 c192→384 k1 | 0.254 | 0.221 | **1.15×** | 1.54× | 3.43× |
| rec 3x208 c384→768 k1 | 0.435 | 0.413 | **1.05×** | 1.36× | 3.11× |

**中位 ≈ 1.05×，最大 1.35×。**

### 最有力的一条：det 480x432 c32→32 k3

这条是**为这个实验量身定做的天然对照**：输入 480×432×32×4 = **26.5 MB**、
输出同为 **26.5 MB**、而权重只有 32×32×9×4 = **36 KB** ⇒ **激活占流量
99.9%**。按「激活是大头」的直觉，砍掉它该有巨大收益。

实测：**1.07×**。

同一条上 `p_wsmall`（权重流量→0）也只有 1.06×——因为这条的权重本来就小。
但 `p_fmaonly`（全部 load 砍掉）**2.55×** ⇒ 时间花在**装载指令**上，不在
字节上（和 §4 / §"已排除"里的定案一致：卡在 **cache line 数 / 局部性 /
装载指令条数**，不是字节量）。

### 对照：权重侧和全 load 侧的份额

- `p_wsmall`（权重流量→0）：1.01 ~ **4.49×**（CTC 头那条最吃权重）
- `p_fmaonly`（全部 load→0）：2.19 ~ **9.95×**

⇒ 时间的大头在**装载指令总量**，其中权重占主导；**激活读流量只占零头**。

## 27.6 结论

**激活流量不是约束。** 即使把激活**读**流量全砍掉（比 fp16 的「减半」还狠），
也只快 1.00~1.35×、中位 1.05×。

**⇒ fp16 激活的预期收益 = 这之上的一个零头，约 0~7%，中位 ~2~3%。**

考虑到改造面是「13 个文件 + 16 个内核 + 布局 + 边界转换」，**收益/代价严重不成
比例，这条路不建议走**。竞品 det 那 1.38× 的缺口**不该记在 fp16 激活账上**——
按本次数据，它更可能来自他们「隐式 GEMM 免 im2col」与「fragment 直接从 device
`simdgroup_load`」这两条**减少装载指令/访存次数**的手法（这才对得上
`p_fmaonly` 比 `p_wsmall` 还大出 2 倍那一段）。

**下一步该动的是「装载指令条数与访存路径」，不是字节宽度。** medium det 里
`n_conv8_mma` 占 33%、`n_conv_dw` 占 22%，是占比够大的位置。
