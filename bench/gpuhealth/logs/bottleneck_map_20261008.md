## 4. 大头定性：1×1 卷积钉在权重带宽墙上

`QPPOCR_METAL_PLAN_DUMP` 取了生产形状，补进 `conv8_variant_scan`
（原来 5 个 case **一个 det 尺寸的 1×1 都没有**，而 1×1 占 det 的 conv8
dispatch 的 98%、占 rec 头全部热点）：

| case | p_base | p_wconst | p_wsmall | p_fmaonly | p_colmaj | p_window |
|---|---|---|---|---|---|---|
| rec 6x208 c192→384 | 0.253 (23%) | 0.109 (52%) | **0.162 (35%)** | 0.073 (78%) | 0.203 (28%) | 0.241 |
| rec 3x208 c384→768 | 0.421 (27%) | 0.202 (57%) | **0.317 (36%)** | 0.137 (83%) | 0.372 (31%) | 0.419 |
| rec 3x208 c768→384 | 0.482 (25%) | 0.215 (57%) | **0.333 (37%)** | 0.141 (87%) | 0.388 (32%) | 0.411 |
| rec ctc head 104x1 | 1.384 (10%) | 0.253 (53%) | **0.394 (34%)** | 0.181 (75%) | 1.468 | 0.736 |

对照 det 3×3 的旧结论（`p_wsmall` 只值 3%）—— **权重墙是 1×1 特有的**。

### ⚠️ 一个「太干净」的假说，已被反例否掉（记下来，别再走一遍）

**假说**：m4×n2 瓦片每 `ci4` 载 4 lanes × 2 float4 = **128 B** 权重，配
32 个 float4-FMA = 128 个标量 FMA → **1 字节权重/FMA**。`rec 6x208 c192→384`
的 FMA = 1248×384×192 = 92 M → 92 MB。实测 0.253 ms → **364 GB/s**；
反推 364 ÷ 1 × 2 = **728 GFLOPS**，而实测 **728.6 GFLOPS**。
**逐位吻合**，看起来是「权重带宽墙」。

**反例（同一张表里就有）**：`p_m8n4` 行 4→8、通道块 2→1，每 FMA 的权重字节
**减半**（4/R，R=4→8），网格公式也正确（`rows:8, nblk:1`，非 `p_t*` 那批故意
错配的）。**实测 0.251 ms，与 p_base 的 0.252 分毫不差——一点没快。**

**结论：这个层不是权重字节带宽受限。** 那个 364 GB/s 的吻合是巧合，我因为
期待它成立而放过了反例。教训同 [[compiler-ate-the-benchmark]]：**读数的
「太干净」本身就是可疑信号，先找反例再下结论。**

### 但也不是「延迟藏不住」——batch 扫描把它排除了（2026-10-08 实测）

`conv8_batch_sweep`（新增）：把网格 y 铺 `batch` 份，**每线程工作量、访存
形状、指令序列一个字节都不改**，只把常驻 warp 数翻倍。这是唯一不靠「砍掉
某样东西」来做的实验（`p_wconst`/`p_wsmall`/`p_fmaonly` 都同时改了延迟与
字节，只能证伪不能定位）。

每份（单张图）时间 ÷ b=1 的比值：

| case | b=1 | b=2 | b=4 | b=8 | b=16 |
|---|---|---|---|---|---|
| rec 6x208 c192→384 | 1.00 | 1.05 | 1.01 | 1.20 | 1.38 |
| rec 3x208 c384→768 | 1.00 | 0.98 | 0.97 | 0.96 | 0.95 |
| det 34x60 c192→384 | 1.00 | 0.98 | 1.10 | 1.27 | 1.37 |

**加 16 倍的常驻 warp，一分钱不赚**，b≥8 还因为工作集溢出 L2 而变差。

⇒ **不是占用率/隐藏能力不足**。`p_fmaonly` 能在**同一网格**上跑到 77–88%
峰值，也早就在提示线程数不是瓶颈。「多合批几条线」「缩小瓦片提并行度」
这两条路**到此为止，别再试**（rec 的 `QPPOCR_REC_GRAIN` 只值 2% 是同一个
结论的另一个侧面）。

### 定案：卡在**权重装载的访存路径**（cache line 数 / 局部性），不是字节、不是延迟

把诊断量按「只改一个自变量」重新排一遍（`rec 6x208 c192→384`，峰值 3273）：

| 变体 | ms | 相对 | 只改了 |
|---|---|---|---|
| `p_base` | 0.252 | 1.00 | — |
| `p_nocoal` | 0.230 | 1.10 | 输入地址钉成常量 ⇒ **输入侧只值 10%** |
| `p_colmaj` | **0.201** | **1.25** | **只改 lane→通道映射**：权重装载由 stride-2 的 8 条半数利用 line 变成 4 条满载 |
| `p_wsmall` | 0.162 | 1.56 | 权重地址压进 1 KB（条数/地址算术全同） |
| `p_wconst` | 0.107 | 2.35 | 权重装载整体消失 |
| `p_fmaonly` | 0.073 | 3.45 | 访存全砍 |

**`p_colmaj` 与 `p_m8n4` 的对照是钥匙**：两者都让权重装载变成 stride-1
（8 条半数 line → 4 条满载）。`p_colmaj` 只动映射，**赚 1.25×**；
`p_m8n4` 同时把输入 gather 从 4 条翻到 8 条、行刻度翻倍，**赚 0**。
⇒ line 数是真变量，`p_m8n4` 只是把自己的收益花在了输入侧。

权重装载占 0.252 里的 0.145（**58%**）；其中「保持条数、只改善局部性」
（`p_wsmall`）就捞回 0.090 ⇒ **约六成是 line 数/局部性，约四成是装载指令
本身**。输入侧（`p_nocoal` 10%）基本免费。

⇒ **处方：让权重装载命中线程组内存**（条数不变、但不再走 L1/L2，且组内
广播）。上限就是 `p_wsmall` 给的 **1.56×**。这与任务 #12 同向，
但**动机要改写成「line 数/局部性」而不是「带宽」**。

`p_t*` 系列（m8×n1 等）的网格是**故意**用 m4n2 公式的（见 `Variant` 注释），
**不能**当瓦片对比的证据（表里 `p_t8n1` 0.232 看着比 base 好，那是网格覆盖
不全，不成立；`p_t4n2` 才是模板自身的控制组，0.316 ≠ 0.252 说明模板也没
标量化到位）。

## 5. 其他已量到的（都是真的，但都不是大头）

- **逐条资源屏障**：det 45.40 → 35.69 ms（21%），rec **0%**。
  需要先给出「Metal 自动 hazard tracking 是否已足够」的正确性论证再谈删除。
  且单次测量噪声 ±15%（det 有 52.10 / 45.40 / 35.69 三个读数），需重复测。
- **CTC 头尾声三趟**：`MatMul.12 → Add.204 → Softmax.2 → argmax`，
  张量 [1,104,18710] = **7.8 MB**。
  `argmax(softmax(x)) == argmax(x)`，而 `n_exit3_argmax` 写回的 `bv`
  （softmax 的最大值）**就是置信度**——所以不能直接删，要改成在 argmax
  里顺带算 logsumexp 得 `exp(m − lse)`。约 0.36 ms/行 ≈ 6%。
- **每次 run 的首次提交冷启动**：~0.6–0.8 ms/行 × 14 次 ≈ 6%。

## 5.5 已落地：列主序映射进 `n_conv8`（2026-10-08）

### 两条映射各管一段，而且互相打架

生产原来只有一条路：`taps==1 && cin4v*nv >= 4096`（**≥256 KB**）走窗口序。
可实测那张权重尺寸阶梯上，两个映射的胜负是**按尺寸分开的**：

| 权重段 | 谁快 | 数据 |
|---|---|---|
| 288 KB（rec 6x208 c192→384 等，**频率最高的两档** 94+80 条 dispatch） | **列主序 1.25×** | p_window 0.239 ≈ p_base 0.252（只值 5%），p_colmaj **0.201** |
| 8771 KB（CTC 头 104x1，12 条） | **窗口序 1.9×** | p_window 0.733，p_colmaj 1.464（**反而更差 0.92×**） |

因果很直白：288 KB 本来就躺在 L2 里，窗口序省的复用距离**没用**，赚的是
lane 连续（权重装载 8 条半数利用的 line → 4 条满载）；8771 KB 装不进
L2，复用距离才是命门。

### 先试了「两个一起用」——被数据否掉

`p_colmajw`（窗口序 + 窗内列主序，`probe_p_colmajw.metal`）在 CTC 头上拿到
**2.00×**（比单独窗口序的 1.51× 还好），可在 **288 KB 那档反而不如单纯的
`p_colmaj`**——窗口序把 lane 的连续通道**拆开了**，列主序就没法把一条装载
填满。**两者不是正交的**，叠加等于互相拆台。于是回到「按尺寸切两套」，
但阈值取多少**原来没有数据**：

| 生产权重段（`QPPOCR_METAL_PLAN_DUMP`，750 条 taps==1） | |
|---|---|
| ≤ 1152 KB（含 288 KB 那两档高频） | 有 |
| **1152 KB ~ 8771 KB** | **一条都没有** |
| 8771 KB（CTC 头） | 有 |

⇒ 阈值落在 1152 KB~8771 KB 之间**随便取都不改变任何一条生产 dispatch 的
去向**。取 **4 MB**（`cin4v*nv >= 65536`），离两端都留足余量。

### 最终映射（三路）

```metal
uint n4, m0, n4b;   // n4b = 第二列；列主序下它**不**等于 n4+1（= n4+nh）
if (taps == 1u && cin4v * nv >= 65536u) { …窗口序，列主序 lane… }   // ≥4 MB
else if (taps == 1u)                    { n4 = gid % nh; n4b = n4 + nh; … } // 列主序
else                                    { n4 = (gid % nh) * 2u; n4b = n4 + 1u; … } // 原 stride-2
```

**位级一致**的论证：每个输出元素仍然按 `ci4` 升序累加，改的只是「哪条线程
算哪个元素」。探针误差与 `p_base` 完全同位（2.24e-8 / 2.98e-8 / 3.73e-8 /
1.86e-8），且 30/30 测试通过（含 4 条整图 CPU 对拍）。

### 端到端收益：**12/12 一致，中位 −3.0%**

`bench/gpuhealth/ab.sh`（新写）——**必须奇偶轮换序**：固定「先 new 后 old」
时，连代码逐字相同的阶段都显示 new 快 6~15%，那是**次序效应**（一小时内
第二次跑更热），它和要量的效应同一量级。换序后它在一轮内对称抵消。
10 张图 × 12 轮配对：

| 指标 | 中位配对差 | 相对 | 12 轮符号 |
|---|---|---|---|
| det | −1.95 ms | **−5.4%** | 全负 |
| line（rec） | −4.15 ms | −2.6% | 全负 |
| total | −5.95 ms | **−3.0%** | 全负 |

偶轮里 `old` 先跑、`new` 后跑，`new` 仍胜——纯次序效应在那里会**翻号**，
所以这是真效应。det 也变快是**应该的**：det 的 conv8 dispatch **98% 是
1×1**，吃的是同一条改动（这也说明 **det 不能当对照**，一度想用它验次序
效应，想错了）。

绝对时间在 12 轮里从 ~165 漂到 ~200 ms/img（±20%），**所以只看配对差**。

## 5.6 落地下一步之前：`p_wsmall` 那 1.56× 被列主序吃掉了吗？（答：没有）

任务 #12（线程组暂存权重切片）的上限取自 **`p_wsmall` 的 1.56×**——可那是
拿 **`p_base`** 当基线量的，那时列主序还没进生产。列主序改的正是「一条装载
指令横跨几条 line」，`p_wsmall` 改的是「地址 footprint 小到常驻」；**两者
可能大量重叠**，不先验就去写暂存，很可能白干。于是加了诊断变体
`p_colmajsmall`（= `p_colmaj` + 与 `p_wsmall` **逐字相同**的地址掩码）。

`SMALL/colmaj` 一列就是答案：

|---|---|---|---|---|
| rec 6x208 c192→384（热） | 0.303 | 0.274 (1.11×) | 0.222 | **1.23×** |
| rec 3x208 c384→768（热） | 0.488 | 0.514 | 0.437 | **1.18×** |
| rec 3x208 c768→384（热） | 0.526 | 0.518 | 0.457 | **1.13×** |
| rec 6x208 c384→384（576K） | 0.630 | 0.574 | 0.481 | **1.19×** |
| det 34x60 c192→384 | 0.519 | 0.471 | 0.392 | **1.20×** |
| det 34x60 c384→192 | 0.507 | 0.437 | 0.390 | **1.12×** |
| det 17x30 c384→768 | 0.393 | 0.417 | 0.369 | **1.13×** |

**结论：余量还在，而且是叠加的两份。** 每个热 1×1 形状上，列主序之上再掩

之上再拿 1.13–1.23×；conv8 占 rec 的 81%、rec 占端到端 ~80% ⇒ 端到端 ~10%。

顺带两条**反向**证据（都印证生产的门是对的）：

- `p_colmaj` 在 **3×3 上是负收益**（rec k3 0.85×、det 480x432 k3 0.69×）
  ⇒ 列主序**必须**只在 `taps==1` 生效，生产就是这么抄的。
- `p_colmaj` 在 **CTC 头（8771 KB）也是负收益**（0.86×）⇒ ≥4 MB 走窗口序的
  门也是对的。`p_colmajsmall` 在那 2.55× 只是因为掩码把 8771 KB 压成了
  常驻小窗——**那不是可以照抄的处方**，是诊断。

## 5.7 线程组暂存权重切片：**实测是死路**（任务 #12 关闭）

5.6 验明「列主序之上还有 1.13–1.23×」之后就照计划落了 `p_wstage`：每个
线程组把一层权重的 `4 行 × nv 列`**协作搬进组内存**（那是一段连续内存，
纯连续拷贝 ⇒ 与 `p_colmaj` **位级一致**，实测误差逐位相同：2.24e-8 /
2.98e-8 / 3.73e-8 / 1.86e-8），热循环改从组内存读。全局流量按
`256/(4nv) ≈ 5.3×` 下降。

**结果：热形状全面变慢。**

### 一个被自己否掉的中间假说，记下来

变慢的程度看着**随切片大小单调**（nv=48 → 1.03×，nv=192 → 0.58×），
于是我先判成「16 KB 组内存吃了**占用率**」——若成立，说明想法没错、只是
颗粒太粗（改暂存一个 warp 真正要的 32 列 = 2 KB 就能转正）。**这条判错了。**

`p_wstage_nb`（把两处 `threadgroup_barrier` 全删、其余一字不改，故意算错、
只看时间）把两者劈开：占用率的代价**照付**、屏障的代价**归零**。结果删掉
屏障就捞回了大头（0.65→0.92、0.60→0.81、0.78→1.17、0.83→0.95）——
**贵的是屏障，不是占用率**（真正的趋势是屏障数 = `2×cin4v`，不是切片大小：
cin4v=48 的 0.98× 对 cin4v=192 的 0.60×）。

### 判词：两个独立的理由，都说这条路不通

1. **屏障很贵**：每 `(t, ci4)` 一对，`cin4v=192` 就是 384 对。原来的权重
   装载**彼此独立、可以流水**，硬件把延迟藏住了；插一对同步屏障就把这份
   重叠**掐断**，省下的流量远抵不上丢掉的并行。
2. **就算把屏障全删掉，也赢不了列主序**：`wstage_nb` 对 `colmaj` 是
   0.80–1.08×（多数行更差）。组内存那趟往返 + 16 KB 静态切片的占用代价，
   本身就 ≥ 硬件缓存做同样事省下的流量。

⇒ **线程组暂存权重切片，关闭。** 5.6 那 1.13–1.23× 的余量是**真的**，但
它不是「搬进组内存」能兑现的——那是 `p_wsmall` 用「把地址掩成常驻」诊断
出来的，生产里没有对应的合法手段。**权重装载这条路，到此为止。**

  只值 2% 是同一个结论。
- **「减小每 FMA 的权重字节」**：`p_m8n4` 字节减半、收益 0。
- **「加大行分块 R」**：`p_r8`/`p_t8n2`/`p_t16n*` 全部更差（寄存器压力）。
- **「输入侧 coalescing」**：`p_nocoal` 只值 10%，`p_k1fast` 反而更差

- **「窗口序 + 列主序叠成一条路，就不需要按尺寸切阈值了」**：`p_colmajw`

  装载。**两者不正交**。见 5.5。
- **「用 det 当 A/B 的对照」（思路错）**：det 的 conv8 dispatch **98% 是
  1×1**，跟 rec 吃同一条改动，不是对照组。用它验次序效应会得出反向结论。
  真正好用的对照是**奇偶轮换序**（见 5.5）。
- **「把权重搬进线程组内存」**：`p_wstage` 0.58–0.98×（热形状全面更慢）；

  往返 + 16 KB 静态切片的占用代价 ≥ 省下的流量。**两个独立理由，都否。**

- **别被「单调趋势」骗**：`p_wstage` 的变慢程度随切片大小单调（nv=48 →

  `2×cin4v`。教训同 [[compiler-ate-the-benchmark]]：**一个漂亮的单调关系
  也要先做对照实验再采信**（这里对照就是 `p_wstage_nb`）。

## 7. 修正（2026-10-09）：第 6 节的排序是错的，因为逐内核剖析的份额不可信

第 6 节按「逐内核剖析的毫秒数」排期望值。**那个排法不成立**，本节给出
替代方法与实测结论。改动前先读这一节，别照第 6 节去做。

### 7.1 唯一可信的归因法：**消融**（ablate），不是剖析

`QPPOCR_GPU_KERNEL_PROF` 的**逐内核份额**不可用于排序，同一份代码里
两个方向的偏差同时存在：

| 内核族 | 剖析占该 plan | 消融实测（端到端） | 偏差 |
|---|---|---|---|
| `n_softmax`（整族） | 9.1% | **2.6%** | 剖析高估 3.5× |
| `n_transpose_nd`+`n_reduce_last`+`n_attn_mm` | 16% | **1.0%** | 剖析高估 16× |
| det 整 plan | 34.22 ms | 29.8 ms | 1.15×（**这个准**） |

同一次剖析里，相邻两个 plan 的偏差差一个数量级。**所以「prof 里排前面
就去优化它」是错的**——第 6 节的第 2、3 条正是这么排出来的。

可信的做法是**消融**：把内核换成空实现，量端到端差值。配套工具已经
有了（`bench/gpuhealth/ab.sh` + 保留二进制），流程是

1. `health.sh` 过门禁；
2. 改一个内核 → `cargo build --release -p qppocr-cli --features qppocr/gpu`；
3. `ab.sh <新> <旧> <图片数>`，**看配对差中位数**。

### 7.2 消融的**有效性前提**（这一步踩过坑，务必先验）

**消融只有在不改变下游工作量时才有效。** det 的输出决定**切出多少行**，
行数决定 rec 跑几次（每图 ~12 次）。所以：

- **det 里出现过的内核不能整体消融**——det 输出变垃圾 ⇒ 行数暴涨/归零，
  量到的是「rec 跑了几次」而不是「这个内核多贵」。
- 实测两个反例：
  - 把 `n_conv8` 整体置空 → det 输出为空 ⇒ **整个 rec 阶段一次都没跑**，
    读数 83.5 ms/img（看着像 −45%），**这个数完全无效**。
  - 把 `n_elem` 整体置空 → 行数涨到 ~11 倍，读数 1417 ms/img。
- **rec 专属的内核可以安全消融**（`n_transpose_nd` / `n_reduce_last` /
  `n_attn_mm` / `n_softmax`）——它们只影响文本内容，不影响行数。

**验法（一分钟）**：两次跑各自数 `QPPOCR_GPU_BUILD_TIME=1` 打印的
`输入 [1, 3, 48, …]` 计划行数，相等才算数。基准是 img-004 的 18。

### 7.3 实测结论（都是端到端、配对差）

| 目标 | 结果 | 判词 |
|---|---|---|
| CTC 头 `n_softmax` 整族 | **−2.6%**（中位配对差，n=4；单次 153.2→149.4） | 真的，但**封顶 2.6%** |
| `phase 2b` 单线程串行求和（单独置空） | −2.5% | 几乎就是上面那 2.6% 的全部 |
| `n_transpose_nd`+`n_reduce_last`+`n_attn_mm` | −1.0% | 剖析说 16%，实测 1% |
| det 逐条资源屏障（`QPPOCR_METAL_NO_BARRIER`） | 中位 +4.5、均值 **−0.05** | **测不到收益**，第 6 节第 3 条作废；且该开关本身会算错数 |
| CTC 头 conv8 层（`MatMul.12`，cin=120/co=18712/m=8） | ~0 | 权重只有 **9 MB**/run，不是以为的 57 MB |

### 7.4 `n_softmax` 的 phase 2b：**知道病根，但没有位级安全的处方**

`n_softmax.metal` 的 phase 2b 把这 18710 个元素全交给**一个 lane** 顺序
取（`if (lid == 0u)`），是 rec 里唯一能一眼看出的结构性缺陷。**三种改法
都试过，全部无效或不能要**：

- **8 条链摊到 8 个线程**（链内次序逐位不变 ⇒ 位级安全）：读数 **160.7**
  （更慢）。原因：8 条链本来就在同一个线程里独立发射、已经吃满了这 8 路
  MLP；摊成 8 个 lane 只是把 8 条独立装载换成 1 条 warp 装载，MLP 不变
  而多一个屏障。
- **单线程内联树**（`(a+b)+(c+d)` 风格）：154.0 ≈ 基准，**无收益**。
- **全 256 线程并行归约**（快，但**改加法次序**）：中位 −4.6 但均值 −0.87，
  6 轮里 2 轮反向 20 ms——而且**不能要**：`inv` 的末位变化会经
  `p_j = e_j × inv` 传导到 argmax，而那正是仓库一直在防的
  「razor-thin 时间步翻 CTC 单字」那类失败。

**未验证的位级安全方向**（留给下次，别重复上面三条）：把 8 个标量装载
换成 2 条 `float4`（`d4[t*2]` / `d4[t*2+1]`，链内次序不变）——但需先
确认 `obase % 4 == 0`（`cpad` 是 cpad4、`out_off` 按 word 对齐，大概率
成立），且可能因在飞装载数从 8 降到 2 而更慢（同 8 线程版的道理）。

### 7.5 现在还剩什么

按**已实测**的份额，端到端 153.2 ms/img 里可动的部分加起来 **<5%**，
而且**低于本机 A/B 的噪声底**（单次读数 ±15%，同一份代码连跑 2 轮
±20 ms）。第 6 节那三条「~6%」全部落空以后，**没有已识别的、大于 5%
的杠杆了**。

> ⚠️ **上面这句当天就被 §8 推翻了。** 漏掉的大头是 **rec 的 `n_conv8`
> 本身（44%）**——它在第 8 节之前**从没被有效消融过**（整体置空会打断
> det 的切行）。§7 只证明了「rec 里除 conv8 之外的那些内核」都很小，
> 不能推出「没有大杠杆」。

det 侧（29.8 ms，剖析对它是准的）内部：`n_conv8` 20.78 / 34.22 = 61%
（已做过列主序），其次 `n_conv_dw` 3.93（11.5%，**地图里从没查过**）、
`n_convt` 2.07、`n_channel` 1.68、`n_elem` 1.33。**`n_conv_dw` 是唯一
没被探针碰过的一块**，量级 2.6% 端到端——想做的话从这里开始，并且
按 7.1/7.2 的规矩来（它是 det 内核，不能整体消融，得找别的对照法）。

### 7.6 一条方法论

**先问「我能用一次消融把这条假说证实/证伪吗」，再去建模型。** 本轮在
`convt`/`elem`/`transpose` 的墙上绕了很久，全是因为拿剖析份额当事实；
而两个消融（softmax 2.6%、rec 专属 1.0%）各只花了一次构建。同
[[compiler-ate-the-benchmark]]、[[ab-order-effect-swamps-small-gains]]。

## 8. 大头找到了：rec 的 `n_conv8` 是 44%，而且从没被有效消融过

### 8.1 先修工具：**rec 专属消融**（`QPPOCR_METAL_STUB_REC`）

第 7 节说过「det 里出现过的内核不能整体消融」。但 rec 是 det 的**下游**：
切多少行由 det 的输出决定，rec 的输出只是文本、**不回馈给任何调度决策**。
所以「只跳过 rec 计划（`argmax_exit`）的某个内核」是**有效**消融——rec 仍
跑同样的次数。这才是量 conv8 的正确姿势，第 7 节那次整体置空作废的原因
是它连 det 一起打了。

```
QPPOCR_METAL_STUB_REC=n_conv8,n_conv     # 按内核名
QPPOCR_METAL_STUB_REC=@MatMul.12         # 按节点名（`@` 前缀，精确匹配）
```
实现在 `session.rs:run()` 的两条派发路径上（切块路径与整块路径都改了），
每次 rec run 都会往 stderr 喊一句「消融模式…数值无效」以免忘记。

**有效性自检（必做）**：跑一遍数 `QPPOCR_GPU_PROF=1` 里的 `run#` 条数，
两变体必须相等。本次实测 plain=222 / 消融=222（另有 171 条 rec 被跳过），
`base` 行数也一致（10.5 行/图 → 切行未受影响）。

### 8.2 结果：**rec `n_conv8`+`n_conv` = −72.95 ms/img（−44%）**

交错 A/B，`bench/gpuhealth/bin/qppocr-rec8off` vs `qppocr-plain`（**同一个
二进制**，只差一个环境变量），40 图 × 4 轮：

| 轮 | det | line | total |
|---|---|---|---|
| 1 | +0.00 | −72.80 | −72.90 |
| 2 | +0.00 | −73.00 | −73.00 |
| 3 | −1.00 | −77.80 | −78.90 |
| 4 | +0.80 | −72.50 | −71.90 |

**中位 total −72.95（n=4）**，164.5 → 91.6 ms/img。det 列恒为 0（本来就是
rec-only 消融，这就是内建的对照组）；4/4 轮同号同量级，**远高于噪声底**。
日志 `logs/ab_20261009_004336.log`。

⇒ 端到端 164.5 ms/img 里，**rec 的 conv8 占 73 ms = 44%**。这与第 2 节
「rec 头内部 n_conv8 占 81%」× 第 1 节「rec 占 64%」≈ 52% 同向（差的那
8 个点是 n_conv/其它 rec 内核，本次一并跳过）。

### 8.3 这次的「13×」比剖析份额靠谱：**算术强度 75 FLOP/byte**

从 `QPPOCR_METAL_PLAN_DUMP` 逐条读 `m / cin / co / taps`（**注意：dump 里
的 `m` 就是位置数**；`out=[1,29,18710]` 这种扁平形状**不能**取 `out[2:]`
当位置数——我第一版脚本这么算，把 `MatMul.12` 的 MAC 数放大了 645 倍）：

单次 rec run（`img-004`，`[1,3,48,232]`，173 dispatch）：

| | 值 |
|---|---|
| conv8 dispatch 数 | 52 |
| MACs | 785 M（= 1.57 GFLOP） |
| 权重流量 | 20.8 MB |
| **算术强度** | **75 FLOP/byte** |
| 机器脊点 | **~43 FLOP/byte**（**实测** 3.34 TFLOPS ÷ 78 GB/s） |
| 理论下界 | 算力 0.47 ms / 带宽 0.27 ms ⇒ **算力主导** |
| **实测** | **6.63 ms**（= 72.95 ms ÷ **11** run，除数见 §9.1） |
| ⇒ 差距 | **~14×**（单计划）；整图口径见下 |

> ⚠️ **本节当初写的是「÷ 12 run」和「13×」。除数是错的**——真实是每图
> 11 个 rec 计划（§9.1 给出计数方法）。按整图口径（11 个计划合计 28.35 GFLOP）
> 重算：**72.95 ms ⇒ 389 GFLOPS**，对本机实测峰值 3.34 TFLOPS = **8.6×**。
> 比单计划的 14× 好看，是因为宽计划（w=832）把权重摊得更薄、强度更高。
> **引用余量时用 8.6×（整图），不要用单计划的 14×。**

两个机器常数都**用本机实测值**，不用规格书：
- **FP32 FMA 峰值 = 3.34 TFLOPS**（`cargo test fma_peak_reference`，
  `grid=2560` 档；规格书的 4.6 TFLOPS 拿不到，别再用它算脊点）。
- 带宽 78 GB/s（`health.sh` 同期读数；文件头记的健康值是 83）。

算术强度 75 > 脊点 43 ⇒ **理想情况下这个算子该是算力受限**，而不是访存
受限。这和第 4 节的探针结论（`p_fmaonly` 能到 77–88% 峰值、`p_wsmall`
只捞回 1.56×）**不矛盾**：探针说的是「在现有内核结构里访存占 58%」，
这里说的是「换一个结构的话，算力才是本征下界」。两者之间的差，就是
那 **13×**。

**92.4% 的 MAC 在 `taps==1`（1×1 / MatMul）那条路上**，而且**没有单层
超过 8.3%**（最大是 CTC 头 `MatMul.12` 8.3%，其次 `Conv.49/50/52/53`
各 6.5%）。所以这不是某一层的问题——是**这条 1×1 路径的系统性结构问题**。
按 `taps` 分组：`taps=1` 48 条 725.7 M（92.4%）、`taps=4` 2 条 3.3%、
`taps=9` 2 条 4.3%。

**另一条线索（本轮没时间验，记下来）**：同一个 `fma_peak_reference`
显示峰值**要 `grid ≥ 810` 才拿得到**——`grid=13` 只有 1778.9 GFLOPS
（53% 峰值）、`grid=102` 才到 3034.4（91%）。而 rec 的 conv8 dispatch
**网格是 5 / 9 / 17 / 74**，全都远在 810 以下。若这个网格依赖在**短突发**
的真实 dispatch 上也成立（第 4 节提过真实 dispatch 吃的是固定开销与访存
停顿、不是稳态带宽，所以**未必成立**），那就意味着连一个完美的内核也上
不去——**先验这个，再谈重写**：把 rec 的 1×1 层按网格大小分档，量
`grid≥810` 那档（如 `MatMul.12` grid=74…也不是）的实际 FMA 效率。

另一条独立线索：`p_base` 在探针形状 `rec 6x208 c192→384` 上做到
**0.73 TFLOPS**，而真实 rec 形状平均只有 **0.26 TFLOPS** —— 同一份内核、
**2.8× 的差距来自形状本身**（真实形状 m 小得多：174 vs 1248）。

### 8.4 两个「标准处方」**都已经量过、都是死路**——别重开

想把「每次权重装载只喂 4 个位置」摊薄，只有两条路，第 2/5.7 节都已关闭：

- **加大行分块（R 4→8）**：`p_r8`（rows 8, nblk 2, m8×n2）**全面更差**
  ——累加器翻倍到 64 个寄存器，寄存器压力吃掉全部收益。
- **权重进线程组内存**：`p_wstage` 0.58–0.98×，删屏障的 `p_wstage_nb` 仍
  赢不了列主序。**§5.7 判词：两个独立理由，都否。**
- 其余（`p_m8n4` 字节减半 0 收益、`p_r8/p_t8n2/p_t16n*` 更差、
  `p_nocoal` 只 10%、`p_k1fast` 更差）见第 6 节列表。

### 8.5 所以下一步的**真问题**

已经不是「再调一个参数」，而是：**这条 1×1 路径每 FMA 要搬 ~6 个 float
（0.67 FLOP/byte 的寄存器级视野），而两条标准缓解路径都被寄存器/屏障
堵死。** 还没被量过的方向只剩结构性的：

1. **两级 GEMM**（线程组内先协作把输入/权重瓦片铺进组内存、再各自算）
   ——与 `p_wstage` 只搬权重不同，这个要**双缓冲**且要能把屏障藏进流水，
   `p_wstage_nb` 的教训（屏障掐断流水重叠）是这里的预警。
2. **换维（转置）**：让 K 走连续地址、M 走 stride，把「每次 FMA 的装载
   条数」换成「装载利用率」——但 `p_colmaj` 已经把 N 侧做成满载，
   再换维要重新论证不会砸掉输入侧的广播。
3. 接受现状：44% 是**已识别的上限**，而 13× 的理论余量在寄存器压力与
   Metal 的 L1/L2 行为下拿不到。

**开工前先跑 `health.sh`**：本次测量后半段机器明显漂了（baseline 164 →
216 → 224 ms/img，`@MatMul.12` 那轮 A/B 的 **det 列出现 −28.3** ——
rec-only 消融的 det 必须恒为 0，那一轮直接判废）。**det 列是 rec-only
消融的内建对照，非 0 就整轮作废**，这条要加进判读规矩。
（`@MatMul.12` 单消融在可用轮次上是 line −4.7 / −23.6 / −9.9，中位
−10.8 ≈ conv8 那 73 ms 的 15%，与它 8.3% 的 MAC 份额、43% 的权重份额
大致对得上，但**这轮噪声太大，只作线索不作结论**。）

### 8.6 方法论（补 §7.6）

**「整体置空」和「下游专属置空」是两种工具，别因为前者的废数就放弃消融。**
第 7 节把 `n_conv8` 整体置空量废了，我当时的结论是「conv8 不能消融」——
正确的结论是「**要找一个不改变下游工作量的消融点**」，而 det/rec 这条
边界天然就是。工具就在手边（`argmax_exit` 一直是个会话字段），
晚了两轮才想到。

## 9. 整图预算定案 + 关掉六个候选（2026-10-09 下半场）

### 9.1 除数修正：每图 **11 个 rec 计划**（不是 12，也不是 18.67）

「18.67 次/图」是数 `消融模式` 行数数出来的，但那次跑的是 **`bench` 子命令**：
bench 是 **1 轮 warmup + N 轮计时**，`--rounds 1` 就是**两遍语料**。所以
56 条 = 3 图 × 2 遍 × ~9.3 计划——**那是「执行次数」，不是「计划数」**。

直接数（**单图普通调用**，不走 bench）：

| 图 | rec 执行次数 | 计划转储里的 rec 计划数 |
|---|---|---|
| img-001 | 10 | — |
| img-004 | 11 | **11**（另有 6 个 det 计划，合计 17） |

⇒ **每图 11 个 rec 计划**，72.95 ÷ 11 = **6.63 ms/计划**。
（旁证：剖析器记的 832 宽计划 conv8 = 11.60 ms，而 832 是最宽档；
11 个计划的中位宽 ~360，11.60 × 360/832 ≈ 5.0 ms，同量级 ✓）

### 9.2 整图预算：**这是现在唯一该引用的基准表**（100 图）

| | total | det | line | 占比 |
|---|---|---|---|---|
| plain | **171.4** | 31.7 | **138.5** | det 18.5% / rec 80.8% |
| `rec8off`（跳过 conv8+n_conv） | 94.7 | **31.7** | 61.8 | — |
| 差 | | **0** | **−76.7** | **conv8+n_conv = 44.7%** |

`det` 列两变体**逐位相同**（31.7 / 31.7）——rec-only 消融的内建对照组通过。

### 9.3 其余 **12 个内核族合起来只有 9.4%**——这里没有大头

逐族消融 A/B（同一个二进制 + 一个环境变量，交错 4 轮，30 图，中位配对差）：

| 消融 | det | line | **total** |
|---|---|---|---|
| `n_elem` | −0.10 | −1.05 | **−1.10** |
| `n_channel` | +0.00 | −1.40 | **−1.10** |
| `n_conv_dw` | +0.00 | −2.60 | **−2.30** |
| **全部关掉**（`qppocr-off-all`） | −0.20 | −92.80 | **−93.00** |

- 12 个族的**真实墙钟合计** = 93.0 − 76.7 = **16.1 ms/img（9.4%）**；单族
  只有 1–2 ms。**逐族去抠没有期望值**，这条可以关掉。
- 全部关掉后 `line` 仍剩 **45.7 ms/img** —— 见 9.4，**那是假象**。

### 9.4 「45.7 ms 无人认领」是**测量假象**（自我更正，务必看）

我先拿 **6 图** `off-all` 的 `rec_infer`（37.3）去比**单张 img-004** 的
`run()` 墙钟之和（3.28），得出「~34 ms 主机侧开销」。**错在口径**——
一边是语料中位数、一边是单图，不可比。

同一张图两边都量：

| img-004 | `rec_infer_ms` | Σ `run()` 墙钟 | 差 |
|---|---|---|---|
| plain | 89.9 | 88.9 | **1%** |
| `off-all` | 11.3 | 3.28 | 8.0 |

⇒ **内核真跑的时候，主机侧几乎完全不暴露**（89.9 ≈ 88.9）。那 8 ms 只在
GPU 闲着时才露出来（pack ~1.3 + CTC 解码 ~6.7）。
**「rec 有 20%+ 主机侧开销」这个说法作废**，别拿它当优化目标。

### 9.5 `rec_pre_ms` / `rec_post_ms` **恒为 0**（字段从来没人写）

```rust
line += t.cls_ms + t.rec_pre_ms + t.rec_infer_ms + t.rec_post_ms;
```
`rec_pre_ms`/`rec_post_ms` 在整个仓库里**只有声明、没有赋值**。实测
`line = cls + rec_infer`（3.9 + 110.9 = 114.8 ✓）。所以 rec 的主机开销
**只能从 `rec_infer` 内部反推**。
已在 bench 表尾加了 4 列（`cls/img recpre/img recinf/img recpost/img`）：
新列**只往后接**，`ab.sh` 取 `$2..$5`（total det line wall）不受影响。

### 9.6 逐内核剖析的**绝对值与份额都不可信**（第 6 节翻车的根因）

- 同一份 conv8：w=232 报 **6.20 ms**、w=272 报 **3.60 ms**——工作量只差
  17%，读数差 72%。
- 该模式下 device 合计会**超过墙钟**（run#1：设备 3.17 vs 墙钟 2.06）。
  采样屏障串行化把每条 dispatch 都拉长，**条数越多拉得越狠**。

**用法**：只看「有哪些内核、各多少条」的**结构**；**不要**拿它的份额去
排序优化目标。本次 12 个族的剖析份额预测 20/16/9 ms，实测 1.1/1.1/2.3 ms
——**差一个数量级**。（唯一对得上的一次是 n_conv8 占 rec 的 55% vs 消融
给的 44.6%，属巧合级。）

### 9.7 静态区重放：每次 rec run 重写 21 MB，实测 **0.5 ms**

新增计时（`ensure_statics`）后：

```
[static] 缓存命中重放静态区：写 20.99/跳 39.70 MB（337 块），耗时 0.50 ms
```

11 次/图 ⇒ **5.5 ms/img（3.2%）**。
机制：`blobs` 是**全局单一的「最后触碰者」清单**，A→B 交替时
`g.blobs != B.recipe` 就整份重放，**哪怕 B 自己那片 arena 根本没被动过**。
理论上可省，但改它要动 **arena 归属判定**——这台机器被 arena 越界
打瘸过不止一次，**3% 不值得冒这个险**。先记着。

### 9.8 顺手修掉两条过时说法

- 微基准里「每条 dispatch 固定 ~1 ms」**是打瘸时代的数**。实测边际
  **4 µs/条**（64 条带屏障 0.403 ms / 不带 0.397 ms，屏障本身不要钱）。
- ⚠️ **`qppocr-nobar` 旧 wrapper 指向 `qppocr-base`，而 `qppocr-plain` 指向
  `qppocr-cur`——是两个不同的二进制**。我第一次跑 NO_BARRIER 的 A/B 就是
  新旧对打。换回同一个二进制重跑，**结论不变**（line −0.20），但这类
  错配必须当场发现，不能靠「det 列看着一样」蒙混。

### 9.9 本节关掉的候选（**别重开**）

| 候选 | 结论 | 依据 |
|---|---|---|
| 网格太小 | **否**，只值 1.15–2.3× | `conv8_grid_scaling_real_shapes`（batch 到 192） |
