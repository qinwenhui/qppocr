# n_convt 挖矿记录（2026-10-10）

任务 #36。`n_convt`（ConvTranspose）是 det 里唯一没碰过的大头。

## 0. 先纠一个记错账：flopsmap 把它放大了 4×

`bench/gpuhealth/flopsmap.py` 按 `taps` pro-rate MAC。但 det 的 ConvTranspose
是 **2×2 stride 2**（kH≤sH 且 kW≤sW），每个输出位置**恰由一个 tap 决定**——
`taps=4` 的 pro-rate 在这里是**纯 4× 高估**。

| | flopsmap 记的 | 真实 |
|---|---|---|
| ConvTranspose.0 (64→64, 240×216) | 6.79 GFLOP | **1.699 GFLOP** |
| ConvTranspose.2 (64→4, 480×432) | 1.70 GFLOP | **0.425 GFLOP** |

两条合计 **2.124 GFLOP / 10.11 ms = 210 GFLOPS = 峰值的 6.3%**
（不是原先以为的 25%）。三条下界都不紧：

- 流量下界 66.4 MB ÷ 77 GB/s = **0.86 ms**
- 算力下界 849 M MAC ÷ 1670 GMAC/s = **0.51 ms**
- 实测 **8.20 + 1.91 ms**

⇒ 既不是喂不上，也不是算不动，是**访存路径/装载条数**。这才值得挖。

  那条 `d[...][ci & 3u]` 的 4× 冗余标量重载 + 动态 float4 下标**。

## 2. 两处改动

**(a) `n_convt` 热循环 → ci4 展开**（`crates/qppocr-metal/shaders/n_convt.metal`）
一次读整个 float4、四条 lane 静态取用。同时消掉动态 float4 下标与 4× 冗余装载。
累加次序与标量版逐 ci 相同 ⇒ **位级一致**。**不改网格、不改 dispatch 条数。**

**(b) 新增 `n_convt4w`**（空间分块，一个线程吃 4 个 tap × 4 个相邻 iw）
输入 1 读 4 用、权重 1 读 4 用，装载/float4-FMA 从 **1.06 → 0.31**。
判据（plan.rs 侧，缺一不可）：`kh==kw==2 && sh==sw==2 && inW%4==0 && nv>=4`。
nv=1 那条走 (a) 不走 (b)——(b) 在 nv=1 上只有 1.73×，反不如 (a) 的 2.01×
（16 个 float4 累加器在通道维没并行度时被寄存器压力反噬）。

## 4. 性能判定（**同一次 run 内交错**，不是跨二进制）

`health.sh` 先过：blit 91.52 GB/s、CPU/GPU = 0.6、`recoveryCount=0` ✅。

### 4c. 改动前的 10.11 ms 怎么算

8.20（ConvTranspose.0）+ 1.91（ConvTranspose.2）是**旧二进制、跨 run** 的读数。
按 memory `sequential-cross-binary-compare-is-drift`，**它不进判据**，只作量级参考。
能进判据的只有 4a/4b 里同一次 run 内交错的 6.55 → 2.33。

## 5. 结论

- 家族设备端 **6.55 → 2.33 ms**（−64%），本图 det 合计 **115.0 → 110.1 ms**。
- 端到端 Δdet 中位 **+3.40 ms / 图**（medium，8 图批次）。
- 数值**位级不变**，两内核互差 0.0e0。
- 新内核 `n_convt4w` 走 `PlanBuilder::conv_t_tile`（Metal 默认 true，
  `QPPOCR_METAL_CONVT_TILE=0|off|false` 可关；Vulkan 恒 false）。
- **GLSL/Vulkan 侧没有同步**（本机无 SPIR-V 工具链，签入的 `.spv` 才是真正跑
  的东西）。`n_convt.comp` 仍是标量热循环——正确但慢。这是**有意的分叉**，
  已写进 `n_convt.metal` 头注释；哪天要同步必须**同时重编 `.spv`**。
