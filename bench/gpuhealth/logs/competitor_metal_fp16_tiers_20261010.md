用户要求：整台机器状态良好前提下，用**他们的 harness + 他们文档的配置**，

## 26.2 他们的配置（逐字取自 `docs/metal-m4.md:3`）

```
实测机：macOS VM（Apple M4 paravirt GPU，8 vCPU）
test/Sdcb.SimdPaddleOCR.Tests bench
  --workers 4 --benchmark-kind simd --engine sharp|metal，warmup=1，n=99
  dataset/ 100 张固定图、张张不同尺寸
```

**重点：`--engine metal` 没有精度开关，它天生是 fp16。**
`MetalRunner.cs:42` / `MetalGraph.cs:77-165`：device arena 与常量权重全是 `Half`，
只有输入/输出缓冲是 fp32。所以「fp16 精度」对他们不是选项，是唯一形态。

复现命令（`DOTNET_ROOT=$HOME/.dotnet` 必设，否则 apphost 报 "You must install .NET"）：

```bash
./test/Sdcb.SimdPaddleOCR.Tests/bin/Release/net10.0/Sdcb.SimdPaddleOCR.Tests \
  --engine metal --model {tiny|small|medium} --workers 4 --benchmark-kind simd \
  --warmup 1 --input dataset --out bench-out/metal-<tier>-4w.json
```

## 26.6 本次最大的测量风险：持续负载下降级且短期不回

一次 medium 100 图的 `--rounds 3` 内，单轮从 **30.8s → 41.1s → 46.7s（+52%）**；
让他们和我们的 medium 反复跑，两边都稳定爬到 **~449 ms/图**（冷态 255）。
**静置 5 分钟没有恢复**（冷却后首跑 269，之后仍冲到 449）。

**更正（同日晚些时候补测）：静置更久（约 40 分钟，我写日志这段时间）后确实恢复了。**
复测 health ✅（blit 89.6 GB/s、CPU/GPU 0.9、recoveryCount 0），紧接着 medium
端到端 **274.0 ms/图**，回到冷态区间。⇒ **恢复曲线是分钟级到数十分钟级，
不是「一去不回」**；但 5 分钟绝对不够。要拿冷态绝对值，跑之前得静置够久。

我怀疑是不是「通路掉速」那类打瘸，于是拿现成探针逐项验：

| 探针 | 现值 | 已知/参考 | 判定 |
|---|---|---|---|
| `fma_peak_reference`（fp32 FMA 峰值） | **3545 GFLOPS** | 3.34–3.55 TFLOPS | ✅ 未降 |
| `health.sh` blit 拷贝 | 90 GB/s | ~93 GB/s | ✅ 未降 |
| `dispatch_marginal_cost` 边际 | 0.003 ms/条 | ~0.007 ms/条 | ✅ 未降 |

**所以不是通路打瘸**（那会同时压低带宽），也不是 ALU 降频。**只有「持续多秒的
综合负载」会掉，短探针都测不出来** ⇒ 更像持续功耗/热约束下的稳定态降频，
而且**回不去得比 5 分钟慢得多**。

**⇒ 本文所有绝对数只在「同一对之内」可信；跨时段比较绝对数是错的。**
要一份干净的绝对值，需要**重启后**再跑（重启需要用户同意——他可能在外面
通过向日葵/SSH 连着，我不能自己重启）。

## 26.7 关于「fp16 精度」：我们的 fp16 和他们的不是一回事

- 他们：**整条流水线 fp16**（激活也走 half4）⇒ DRAM 流量直接减半。
- 我们：`QPPOCR_METAL_WF16=1` 只是**权重存 fp16**，激活仍 f32；而且
  `plan.rs:1216/1236` 的 MMA 门里带 `&& !fp16` ⇒ **开了 fp16，每个 1×1 conv
  都掉回 `n_conv8h`**，而 1×1 正是 MMA 收益最大的一类。
- 既有实测：这是 **1.14× 的净亏**，不是收益（见 [[fp16-dead-after-mma]]）。
  用户此前已决定「保持 f32 默认、只留旋钮」。

⇒ **「我们分别以 fp16 跑一遍再比」这个实验做不出公平结论**，因为两边的 fp16
不是同一个东西。要真正对齐，得让我们的**激活**也走 fp16——那是一个内核级改造，
不是翻转旋钮。**本次没有跑我们的 fp16 臂**，理由是它结构上必然更慢，
测出来的数只会误导，而不是回答「能否达到他们的数字」。

## 26.8 ★ 数据集疑云已闭合：corpus100 就是他们生成器的输出

上一节说「他们 dataset 拿不到」。**闭合了**，而且是硬证据：

他们 `test/Sdcb.SimdPaddleOCR.TestData/Program.cs` 是**完全确定性**的
（`:25 const int Seed = 20260830;`），尺寸由 rng 前两抽决定、**早于任何字体**：

```csharp
int width  = 640 + 16 * rng.Next(0, (1800-640)/16 + 1);   // 640..1792
int height = 480 + 16 * rng.Next(0, (1400-480)/16 + 1);   // 480..1392
```

我用 `PPOCR_FONTS_DIR` 指到 macOS `Hiragino Sans GB.ttc` 跑了一遍生成器
（`bench/gpuhealth/gen100/`，100 张 + 一份真值 json），然后逐张比尺寸：

| | |
|---|---|
| **尺寸完全一致** | **100 / 100** |
| corpus100 W min/med/max/mean | 640 / 1224 / 1792 / 1233 |
| gen100     W min/med/max/mean | 与上**完全相同** |
| corpus100 面积 mean | 1.140 MPx |
| gen100    面积 mean | 1.147 MPx（理论值） |
| gen100 `lines/img` | **10.21** |
| 他们文档 lines/img | **~10.1**（1016/1009/1013） |

⇒ **corpus100 = 他们那份 canonical 100 张（同生成器、同 seed）**，
唯一的差别是**字体**（Windows 的 msyh/simhei ↔ macOS 的 Hiragino）。
**「图集不同所以不可比」这个解释到此作废。**

## 26.9 ★ 他们的数字在**他们自己的数据 + 他们自己的代码**上复现不了

拿 `gen100` 跑**他们的 harness + 他们文档的配置**（`--engine metal --workers 4
--benchmark-kind simd --warmup 1`）：

| 档位 | 文档 | gen100 实测（median） | corpus100 实测 | 判定 |
|---|---:|---:|---:|---|
| tiny   | 39.3 | **39.0** | 35.4 | ✅ **复现**（差 0.8%） |
| small  | 54.6 | **68.6** | 68.7 | ❌ 慢 1.26× |
| medium | 107.0 | **257.6** | 255.2 / 269.4 | ❌ 慢 **2.41×** |

分阶段（mean，gen100）：

| 档位 | 阶段 | 文档 | gen100 | 差 |
|---|---|---:|---:|---:|
| tiny   | det_graph | 13.0 | 14.62 | 1.12× |
| small  | det_graph | 13.6 | 17.67 | 1.30× |
| medium | det_graph | 33.1 | **71.78** | **2.17×** |
| medium | rec_graph | 68.9 | **171.38** | **2.49×** |

**且 gen100 与 corpus100 两边读数一致**（255.2/257.6/269.4 同一区间）⇒ 字体也不影响，
**数据集这条线彻底排除**。

**注意 tiny 复现得极准（39.0 vs 39.3），small/medium 复现不了** —— 同机、同码、
同数据，只有模型档位不同。这个「小档准、大档崩」的形状是本次最硬的线索。

## 26.10 workers 扫描：**作废**（次序污染）

我扫了 medium 的 `--workers 1/2/8`，读到 266 / 373 / 466，看着「人越多越慢」。
**但我是按 1→2→8 顺序跑的，而本机持续负载单调爬升 —— 这正是 §26.6 那个爬升，
不是 worker 数的效应**（同 [[ab-order-effect-swamps-small-gains]]）。
⇒ **本次扫描作废，不给结论。** 要量它必须配对交错。顺带一句：文档的 `workers=4`
在独立那次 gen100 跑里给出 257.6，本来就是四次里最好的，**没有证据说文档配错**。

## 26.11 本次结论

1. **能否达到他们文档的数字**：**tiny 能**（39.0 ≤ 39.3，几乎精确复现）；
   **small / medium 不能**（1.26× / 2.41×）。**这跑的是他们的代码 + 他们的数据**，
   所以缺口**不在我们的实现**，也不在数据集。
2. **同机同图**：三档与我们**打平**（0.97 / 1.01 / 0.99，§26.5），与 §18 一致。
3. **可复现的判据**：他们 `docs/metal-m4.md` 的 medium 107.0 在本机**任何一次**
   测量都没接近过（最低 255.2），且这与次序无关（我从未读到过 100 附近的数）。
   **他们自称「paravirt 绝对值偏保守、真机更好」，本机实测在 small/medium 上反了。**
   最可能的解释是**测量条件**（他们 VM 的 GPU 不驱动显示器；本机 WindowServer +
   向日葵 + 屏幕共享在抢 GPU），但这**在本机无法证伪** —— 需要一台同样无显示负载的
   M4 才能判。
4. **测量本身**：本机持续负载下会降级（√已确认会恢复，但需数十分钟）；跨时段比
   绝对值是错的；`workers` 这类小效应**必须配对交错**才量得出来。
