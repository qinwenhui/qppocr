# 对齐修复之后的对拍：tiny/medium 反超，small 输在「每行一次 run」（2026-10-11）

## 1. 结论先行

`cmp_metal.sh`（他们 harness 4w fp16 vs 我们 bench 1w f32，同 100 图、档内交错、3 对取中位）：

| 档位 | 竞品中位 | 我们中位 | 我们/竞品 |
|---|---:|---:|---:|
| tiny | 37.7 | **36.7** | **0.97×（我们快）** |
| small | 70.8 | 87.1 | **1.23×（我们慢）** |
| medium | 382.7 | **346.7** | **0.91×（我们快）** |

上一轮同口径（`competitor_headtohead_20261010.md` §18.1，medium）我们 265.4 对 251.6 = **1.06× 慢**。
**两条 64 B 对齐修复（`27c0279`/`69a4783`）之后口径翻过来了。**

> ⚠️ 绝对数不可跨会话比：同一次会话里两边都从 265/252 漂到 347/383（+31%/+52%），
> 而跑完 `health.sh` 仍是 94.4 GB/s 健康；单跑 medium 又回到 **269.2**（det 90.4 / line 177.6）。
> **只有同一次交错里的配对差算数**——这是 [[sequential-cross-binary-compare-is-drift]] 的第 N 个实例。

## 2. small 那 1.23× 全在 rec，而且是结构性的

竞品 `bench-out/cmp-small.json` 的 `stage_ms_mean`：det 段合计 **23.8**（pre 1.86 + graph 19.84 + post 2.05）、
rec+cls 段合计 **54.1**（crop 2.32 + cls 2.68 + rec_pre 1.16 + **rec_graph 47.50**）。
我们同档：det **21.7**、line **63.5**（其中 `recinf` 60.0）。

⇒ **det 我们更快**（21.7 对 23.8）；差的 9.4 ms 全在 rec/line。

### 2.1 rec 的每次 run 有一个 2.27 ms 的地板

`QPPOCR_GPU_PROF=1` 的 `[metal] run#` 行给出每一次 rec run 的墙钟。small 档 100 图
（warmup+1 轮）共 **1922 次 rec run**，其中 **1776 次是一行**：

* 拟合（n=1776）：**`t = 2.271 + 0.005966·w` ms**（w = 桶宽，h=48 缩放后）
  —— w=96 已经要 2.98~3.25 ms，w=400 要 4.66，w=1000 要 8.24。
* 墙钟里 `编码 0.03 + 等待 3.38` ⇒ **地板全在设备端**，不是主机提交开销。

这 2.27 ms 可以拆开——仓库里现成的两个微基准（`cargo test --release -p qppocr-metal
--lib dispatch_ -- --nocapture`）量过同一件事：

```
[mb]   256 条 dispatch（含逐条 barrier）: 1.103 ms  （边际 0.0043 ms/条）
[mb] 仿 173 条真实名 dispatch（守卫早退，纯开销）: 1.201 ms
```

⇒ 173 条 dispatch 的**机制成本**是 **1.20 ms**（含约 0.25 ms 的命令缓冲往返），
剩下 **~1.07 ms 才是内核真执行的**（小网格、访存延迟受限）。所以地板不是「纯调度税」，
但**按 run 付**，与算了多少无关。
* 同宽**两行合批**：`t(2行) = 2.048 + 0.012025·w`，实测同宽 1 行/2 行比值
  **中位 1.45**（窄 208~456 是 1.22~1.55，宽 944~1176 是 1.69~1.73）
  ⇒ **合批省下的是整整一个地板**（2 行分开跑要付 2 次 ~2.2 ms）。

**每图 ~9.6 次 rec run × 2.27 ms ≈ 21.8 ms**，占 small 的 `recinf`(60.0) **36%**、
占整图(86.5) **25%**。medium 的 rec(173.7) 里同比例约 13% ——
所以**同一个结构缺陷在小模型上才致命**：地板不随模型变小。

### 2.2 为什么合批几乎不发生

`bucket_grain()` 对**无注意力 mask 的 rec**（`exact_width`，small/medium 都是）返回 **8**
（`MetalSession::bucket_grain`），即按 8 px 分桶。语料里每行的自然宽各不相同，
**8 px 桶几乎不重合**：1922 次 run 里只有 134 次是两行、10 次三行（**7%**）。

桶粗一点就能合很多行，代价是最多 `grain` px 的右零填充。

## 3. 桶宽粒度的 A/B（`QPPOCR_REC_GRAIN`，现成开关）

`env_ab.sh`，奇偶轮换序，`--workers 1`：

| 档位 | 粒度 | Δtotal | Δline | Δdet（对照） | 符号 |
|---|---:|---:|---:|---:|---|
| small | 32 | **−5.95** | −6.05 | **+0.00** | 4/4 负 |
| small | 64 | −7.00 | −8.15 | +1.50 | 6/6 负 |
| medium | 64 | −4.70 | **−8.95** | +4.05 | 6/6 负 |

（medium 20 图那轮第 3、4 轮整机爬升 65%（A 235.8→389.6），离散 91 ms，**判废**；
换成 10 图 6 轮重跑才拿到上表那行。）

**对照列 Δdet 在 grain=64 上系统性地正**（+1.5 / +4.05，同号满格）。判据上这属于
「污染不是噪声」，但污染方向是**对我们不利**的：grain=64 的 B 臂做得少、机身更凉，
而本机冷态就慢（[[compiler-ate-the-benchmark]] 记过首跑低 15~40%）。所以真实的
Δline 只会比 −8.15/−8.95 更负，不会更正。grain=32 那轮 Δdet 恰好 +0.00，最干净。

## 4. 代价：逐行文本对拍（100 图 small + 40 图 medium）

`python3 bench/gpuhealth/grain_acc.py`（新脚本，逐图 `--json` 取每行文本）：

| 档位 | 行数 | 文本不同 | 结论 |
|---|---:|---:|---|
| small grain8→32 | 1041 | **0** | 只有置信度第 4 位小数在动 |
| small grain8→64 | 1041 | **0** | 同上；另 0 行丢失 |
| medium grain8→64 | 411 | **0** | 同上 |

置信度扰动的量级：多数 ±0.001，最大一处 0.9791 → 1.0000。
**行数一致（无丢行）、文本逐字符一致。**

### 4.1 对照臂（必须做，否则上面那张表不算数）

[[metal-rec-output-is-nondeterministic]] 记过「同一份二进制连跑两遍、多图路径下
文本会抖」。所以先跑同配置两次的对拍：

* `dump small 8` 跑两遍（两次各 100 个独立进程）→ **1041 行，文本不同 0 行**。

⇒ `grain_acc.py` 走的**一图一进程**路径是确定的，上面 grain 8↔32/64 的零差异
不是「抖动恰好抵消」。**但那条警示针对的是多图共进程路径**（计划/arena 复用），
本工具没覆盖它——若这条改动要落地，得多图路径也做一次同配置对照。

### 为什么这是「要拍板」的：不是加法顺序

`conv1x1_mma` 那类改动是「换个加法顺序」，所以默认开。**桶宽填充不是**——它改的是
送进模型的输入序列长度，注意力的 softmax 分母因此变化。仓库里就有守卫测试把这条
钉死：`crates/qppocr-gpu/src/vulkan/n_kernel_tests.rs::small_rec_pad_*` 断言
`nbad > 0`（填充**必须**改输出），失败信息写着「small rec 已对右零填充不变——
exact_width 的形状税可能可退役」。也就是**这条边界是已知的、有意保守的**，
现有 8 px 是当初按「GT 实测与逐像素精确无差」选的。

## 5. 已落地：粒度 32（用户拍板）

`MetalSession::bucket_grain` / `VulkanSession::bucket_grain` 的
`if self.exact_width { 8 } else { 64 }` → **`{ 32 }`**（两个后端同款，注释里写明
本机无 Vulkan 设备、证据是 Metal 侧的）。**当时没选 64**：窄行（w=96）会填到 128
（相对 +33%），与 `small_rec_pad_*` 守卫用的 24→32 同量级；32 更保守而收益已拿
大半。守卫测试 `small_rec_padding_invariance` 仍成立（32 也填充），无需改断言。
`cargo test --release -p qppocr-gpu --lib` 37 passed、`-p qppocr-metal --lib` 56 passed。

> **§5 那个「没选 64」的理由已被 §7 推翻**：实测 32→64 仍是 −3 ms/图、且
> 1041 行里只有 7 行文本变化、0 处新增错字 ⇒ 已落地为 **64**。留着这段是因为
> 它准确记录了当时的判断依据。

收益：small Δline −6.05 ms/图（−7%）。落地后用 **新默认 vs 强制 `QPPOCR_REC_GRAIN=8`**
（即旧行为）复验：small 绝对数 **86.5 → 81.0**，Δline **+5.85 ms**（6/6 同号、
Δdet **+0.00**、离散 1.0 ms）。

⚠️ **但这还没追平 small**：81.0 对竞品 70.8 = **1.14×**，仍是我们慢。要把 §1 的 1.23×
真正抹平，还得再拿 ~10 ms，而那要靠更粗的粒度（= 更大的数值扰动）或减少每 run 的
173 条 dispatch（内核融合）——两条都超出这次拍板的范围。

### 5.1 落地后的全档对拍复测（`cmp_metal.sh 3 "tiny small medium"`）

| 档位 | 竞品中位 | 我们中位 | 落地前 | 我们/竞品 |
|---|---:|---:|---:|---:|
| tiny | 37.4 | **36.8** | 0.97× | **0.98×（我们快）** |
| small | 68.8 | 80.7 | 1.23× | **1.17×（我们慢，改善）** |
| medium | 374.7 | **335.3** | 0.91× | **0.89×（我们快）** |

我们 small 三对 = 80.4 / 80.7 / **86.9**；前两对与 A/B 的 81.0 咬合，第三对是漂移
（[[sequential-cross-binary-compare-is-drift]]），中位取 80.7。medium 三对两边同步
爬升（竞 312→393、我 290→365），比率仍稳在 0.89×，是同一个整机漂移不是回归。

⇒ 桶宽 32 把 small 的差距从 1.23× 压到 **1.17×**，两个本来赢的档没被拖累。
**但 small 仍输**，缺口定价 ~12 ms/图（80.7−68.8），与 §2 推算的「每图 ~9.6 次 run ×
2.27 ms 地板」同量级 ⇒ **下一步只能去动 run 的次数或 173 条 dispatch 本身**。

## 7. 粒度再抬一级：32 → 64（2026-10-11，用户拍板）

§5 停在 32 的理由是「64 会让窄行 w=96 填到 128（相对 +33%），与守卫测试用的
24→32 同量级」。**这条已经被实测推翻**——相对填充大不等于掉字，代价得量。

### 7.1 机理：32→64 买到的是整整两个 run

§2.1 的地板模型直接给出预测：img-001（10 行）的 rec run 数 **6 → 4**
（32：2×256、2×288、1×384、2×448、1×896、2×1024；64：4×320、3×448、1×896、2×1024），
代价模型 `t = 2.27 − 0.22(n−1) + 0.006·n·W` 预测 **44.6 → 41.2 ms = −3.4 ms**。
（128 也是 4 个 run 但更宽 → 44.6 ms，0 收益；256 只 2 个 run 但 42.7 ms，仍不如 64。）

### 7.2 速度（`env_ab.sh` 交错，small，workers 1，健康态 ~70.5 ms/图）

| 轮 | A tot | B tot | Δtot | Δdet | Δline |
|---:|---:|---:|---:|---:|---:|
| 1 | 70.3 | 67.5 | −2.80 | +0.10 | −2.80 |
| 2 | 71.0 | 67.9 | −3.10 | +0.00 | −3.00 |
| 3 | 70.7 | 70.3 | −0.40 | +0.70 | −1.10 |
| 4~8 | 94.8→112 | — | 漂移，弃 | | |

另一轮 8 次同款：中位 **−2.10**（符号 6/8 负），其中健康态头两轮 −2.80 / −3.10、
Δdet +0.10 / +0.00。⇒ 取 **~3 ms/图**，与 §7.1 的 −3.4 ms 预测咬合。
对照列 Δdet 两批都是 ≈0.00 ⇒ 不是整机漂移（[[ab-variance-must-be-two-sided]]）。

### 7.4 落地形态与复验

`bucket_grain` 的 `if self.exact_width { 32 } else { 64 }` 两个分支**都成了 64**
⇒ 条件没有信息量，**退役 `exact_width` 字段**（Metal / Vulkan 的 session 字段 +
mod.rs 赋值共 6 处），把「注意力 rec 对填充不 invariant」这条知识留在
`bucket_grain` 的注释和 `small_rec_padding_invariance` 守卫里（后者仍断言
`nbad > 0` 且全绿——它是内核级性质，与粒度无关）。

复验（新默认**不设 env** 跑 `grain_acc.py dump small 0`）：
* 与强制的 64 臂 **1041 行逐位一致（含置信度 4 位小数）** ⇒ 落地就是被量的那一臂；
* 与强制的 32 臂文本差 **7 行**（正是 §7.3 那 7 行）；
* 反向 A/B（A = 新默认 64，B = 强制 `QPPOCR_REC_GRAIN=32`）：Δtotal 中位
  **+2.05**（5/6 正）、Δdet −0.20 ⇒ 退回 32 要多付 ~2 ms/图。

`cargo test --release -p qppocr-gpu --lib` 37 passed、`-p qppocr-metal --lib` 57 passed。
