# MMA 装载路径（device 直读 vs threadgroup 中转）2026-10-10

任务 #37。起因：全图几十个内核齐刷刷落在 36~66% 峰值，加上「我们的 fp16 MMA
探针只有 f32 的 0.62×」（与 Apple 的 fp16 = 2× f32 相反），两个反常像是**同一个
共享病根**。读遍全仓四个 MMA 内核（`n_conv8_mma` / `n_conv8_mma3` / 两个探针），
发现 A/B 分片全是 `simdgroup_load` **从 device 直读**，`threadgroup` 只用在尾声
写回——而 Apple 的标准快路是「协作拷贝 → threadgroup → barrier → 取分片」。

**结论：假设被推翻。探针上 +27~46% 是探针自己造成的假象；搬到生产是 −25~45%。**

## 1. 探针（`probe_mm_tg.metal` / `microbench::mm_tg_scan`）

同结构、同网格（64×64 瓦片、256 线程/组）、同数学，只换 A/B 分片的来源。
对照臂 `p_mm_sg` 在**同一次 run** 里跑（不许拿历史读数当对照）。

det 两形状、best-of-15：

| 臂 | c512→1024 (GFLOPS) | c1024→512 |
|---|---|---|
| fp16 device 直读 | 1494 | 1511 |
| fp16 tg 单缓冲 | **2182** | **2241** |
| fp16 tg 双缓冲 | 1854 | 1808 |
| f32 device 直读 | 1437 | 1454 |
| f32 tg 单缓冲 | **1830** | **1873** |
| f32 tg 双缓冲 | 1555 | 1491 |

两条当时读作「结论」的东西：

- **两个 dtype 的 device 直读都封在 1437~1511** —— 看着就是共享病根的签名；
- f32 单缓冲 **+27%/+29%**，fp16 单缓冲 **+46%** —— 看着是全族的大杠杆。

`p_mm_sg` 的历史读数（大形状 M=921600）是 1500/1518，本轮小形状（M=115200）
是 1494/1511 ⇒ 形状缩小（为内存安全，见 §4）没有改变结论，**且机器没有漂**。

## 3. 探针为什么骗人：**B 操作数的转置**

看 §2 那一列 `dev`：**生产的 device 直读本来就有 2209~2467 GFLOPS**，比探针
「中转」臂的 1830 还高。所以探针的 device 臂（1437~1510）根本不是「生产的
device 直读」——它比生产**慢 1.5 倍**，那 1.5 倍是探针自己塞进去的。

差在 B：

| | 布局 | 取分片 |
|---|---|---|
| 探针 `p_mm_*` | `[N,K]`，行 stride = K | `transpose = true` ⇒ **跨步 gather** |
| 生产 `n_conv8_mma` | `[k][n]`，行 stride = nDim | 不转置，`simdgroup_load` 直接可用 |

跨步 gather 本来就慢，而**中转恰好把 gather 抹掉**（低延迟线程组里的跨步读
几乎免费）。生产没有这个缺陷可修，中转就只剩净亏：多一次协作拷贝、多两道
屏障、8 KB 线程组占用（小 m 的 rec 形状掉得最狠，0.63~0.75×）。

### 与已知探针陷阱的关系

memory `probe-wins-dont-transfer-to-production` 记的是**探针剥掉了生产里存在的
成本**（`n_conv_dw` 探针 1.14×、生产 −19%）。这次是**新的一类**：探针**加上了
生产里不存在的成本**——它在**被自己弄坏的基线**上做对照，赢的是修自己捅的娄子。

**判据（可操作）：大赢先查基线臂。** 同一形状下，如果生产内核的**孤立**读数已经
超过探针的「优化」臂，那这个探针量的一定不是它自己声称的东西。

## 4. 顺带修掉的两个真 bug

### 4a. 基准缓冲 > 物理内存 → **GPU 页故障**

`mm_sg_scan` 的缓冲尺寸算法是「各 case 的 m/n/k 各取独立最大值再相乘」：
`m_max * n_max` = 921600 × 18710 ⇒ **34.4 GB**（本机 24 GB），而且 A/W/C
**全绑在偏移 0 上互相覆写**。fp16 只碰 1.9 GB 时三次侥幸过关；加上 f32 臂
（碰 3.8 GB）后 `p_mm_f32_dev` **直接触发 GPU 页故障**（`recoveryCount` 0→1）。

修：每个 case 按自己的精确尺寸分配、A/W/C 三段按元素宽度错开。
`mm_sg_scan` 2.83 GB / `mm_tg_scan` 710 MB。

**故障后 GPU 未瘸**：blit 89.88 GB/s（正常 90~93），且 `p_mm_sg` 对照臂
（1500.5 → 1494.2）无退化 ⇒ 故障前测到的数字可用。

### 4b. 健康门禁在**该报警时**静默返回「健康」

`health.sh` 第 18 行 `msg="recoveryCount=$rec（有过 GPU 页故障）…"` ——
macOS 的 bash 3.2 会把多字节的 `（` 吞进变量名，于是 `$rec` 解析成
未定义变量 `rec（`，`set -u` 下报错、`if` 不成立、`verdict` 保持 0、
**脚本以退出码 0 结束**。也就是说：`recoveryCount != 0` 时门禁输出「✅ 健康」。

修：`${rec}`。顺带扫了 `bench/gpuhealth/*.sh` 其余同名写法（`$var` 紧跟中文
全角标点），只有这一处会真的展开到变量（其余都在单引号 echo 或已加花括号）。

## 5. 仍然成立的副产物

- **双缓冲在两个 dtype 上都慢 15~20%**（fp16 1854 vs 单缓冲 2182；f32 1555/1491
  vs 1830/1873）。Apple 教科书的双缓冲配方在本结构下不划算：暂存翻倍到顶
  （32 KB）压低常驻线程组数。这是真结论——但生产里没有中转，所以也用不上。
- **fp16 相对我们的 f32 没有净胜**：fp16 中转 2182~2241 ≈ 生产 f32 device 直读
  2209~2467。与 memory `fp16-dead-after-mma` 一致。
- **`n_conv8_mma` 自己的天花板 = 2209~2467 GFLOPS = f32 ALU 峰值的 66~74%**
  （长 K 的 det 形状；`c32->64` 只有 1033，那是短 K 问题，`conv8_mma_ksweep` 管）。
  拿它当尺子——**不许拿 3340 算余量**（memory
  `roofline-must-use-kernels-own-ceiling`）。

2. **`n_conv_dw` 24.4 ms**（det 21%）。

4. det 的纯访存节点（`n_elem` ×21、`n_concat_c` ×2、`n_channel` ×7、`n_resize` ×6；
   `Concat.0` 一条搬 212 MB、`Add.158` 159 MB，都已贴着 DRAM 速度）。
