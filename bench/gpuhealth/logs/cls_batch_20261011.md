# cls 合批下限 8 → 32（2026-10-11）

## 1. 靶子

`engine.rs` 的 cls 分批：GPU 侧 `per = cfg.cls_batch.max(8)`，而语料每图
**6~17 行**（corpus100 small，`acc_small_g32.txt` 统计）⇒ 10 行的图跑
`[8,3,48,192]` + `[2,3,48,192]` 两次 run，**白付一个设备端地板**。

`QPPOCR_GPU_PROF=1` 直接看到（img-001，机器偏热态）：

```
run#1 输入 [8, 3, 48, 192]（真实行 8）→ 104 个 dispatch，墙钟 2.72 ms
run#2 输入 [2, 3, 48, 192]（真实行 2）→ 104 个 dispatch，墙钟 2.30 ms
```

**两条都 104 条 dispatch**，而 2 行的那条要 2.30 ms、8 行的才 2.72 ms
⇒ run 内从 2 行加到 8 行只贵 ~0.4 ms，**成本几乎全是 per-run 地板**。

## 2. 合到几？—— 语料统计，32 饱和

```
per=  8 → 每图 cls run 数 1.730（corpus100 共 173 次）
per= 16 →                1.020
per= 32 →                1.000   ← 饱和（语料最大 17 行）
```

**批维不补齐**（只把真实行填进批次维，见 `engine.rs` 的 `cls_batches` 切法），
所以 per 大于图上行数时**没有空行白算**，代价只有内存（32 行 × 48×192×3×4 B
≈ 3.5 MB）。顺带一个副产品：**per 越大计划形状越少**——10 行的图 per=8 要
`(8)` + `(2)` 两个形状，per=32 只要 `(10)`。

## 3. 直测：cls 段 3.17 → 2.44 ms/图

`bench` 的端到端 A/B 被机身漂移吃了（见 §5），所以改用**只量 cls run 的和**：
一图一进程、交错 3 轮 × 5 图（img-001..005），从 `QPPOCR_GPU_PROF` 里挑出
`输入 [N, 3, 48, 192]` 的行累加墙钟。

| 轮 | per=8 | per=32 |
|---|---:|---:|
| 1 | 15.05 ms（9 次 run） | 12.18 ms（5 次） |
| 2 | 16.89 ms（9 次） | 12.65 ms（5 次） |
| 3 | 15.83 ms（9 次） | 11.84 ms（5 次） |
| 5 图合计中位 | **15.83** | **12.18** |
| **每图** | **3.17 ms** | **2.44 ms** |

⇒ **省 0.73 ms/图**，3/3 同号、交织次序（每轮内 8→32 固定，但三轮独立）。

（run 数 9→5 与 §2 的 1.73→1.00 吻合。）

## 4. 逐位不变（这是它能默认开的原因）

批维不参与任何归约，且不补齐 ⇒ 同一行的计算与批内其它行无关。
`grain_acc.py` 一图一进程、corpus100 small 前 30 图 **322 行**对拍：

| 对比 | 结果 |
|---|---|
| 落地后的新默认 vs 强制 `QPPOCR_CLS_BATCH=32` | **322/322 整行逐位一致** |
| 落地后的新默认 vs 强制 `QPPOCR_CLS_BATCH=8` | **322/322 整行逐位一致（含置信度 4 位小数）** |

## 5. 端到端 A/B 为什么只有噪声级——以及它的真因

`env_ab.sh 30 6 QPPOCR_CLS_BATCH=32`（small，workers 1）：

```
轮 1   72.8 / 71.4   Δtot −1.40   Δdet −0.10
轮 2   69.8 / 69.4   Δtot −0.40   Δdet +0.00
轮 3   69.7 / 70.7   Δtot +1.00   Δdet +0.30
轮 4~6  88.9 → 155.4（整机跑飞）
中位 Δtotal −0.90   符号 4/6 负   离散 28.2 ms
```

只看健康的三轮：**−1.40 / −0.40 / +1.00**，中位 −0.40，散布 ±0.7 —— 与 §3
直测的 −0.73 **同号、同量级**，但单看端到端落不进显著。原因有二：

1. 这一档的 gain 本来就小（0.73 / 70 = **1.0%**；tiny 档 32 ms 上是 **2.3%**）；
2. 这台机器在**带宽达标的同时整体爬升**（§5 那张表：69.7 → 155.4 = **+123%**，
   而 `health.sh` 照报 74~89 GB/s 合格）——`env_ab.sh` 的 Δdet 对照列这轮也没能
   挡住（+0.30 / −0.10 是同号的轻度污染）。

⇒ **别拿这轮的端到端中位数当结论**；论据是 §3 的直测 + §2 的机理。

## 6. 落地

`per = cfg.cls_batch.max(8)` → **`.max(32)`**，并加 `QPPOCR_CLS_BATCH` 覆写
整条表达式（量「批多大才够」用；本机就是这样量的）。只动 GPU 分支，
CPU 分支仍是 `max(1)`（批化在 CPU 上 4.12→11.95 ms，早前被回退）。

## 7. 复现

```bash
./bench/gpuhealth/health.sh
# 直测 cls 段（交错，一图一进程）
for arm in 8 32; do
  for i in 001 002 003 004 005; do
    QPPOCR_CLS_BATCH=$arm QPPOCR_GPU_PROF=1 ./target/release/qppocr \
      bench/gpuhealth/corpus100/img-$i.jpg --models models --device metal \
      --tier small --preset balanced --json 2>&1 >/dev/null
  done | # 挑出 输入 [N, 3, 48, 192] 的行累加墙钟
done
# 逐位对拍
python3 bench/gpuhealth/grain_acc.py dump small 0 bench/gpuhealth/logs/a.txt 1 30   # QPPOCR_CLS_BATCH 走环境继承
python3 bench/gpuhealth/grain_acc.py dump small 0 bench/gpuhealth/logs/b.txt 1 30
python3 bench/gpuhealth/grain_acc.py diff bench/gpuhealth/logs/a.txt bench/gpuhealth/logs/b.txt
```
