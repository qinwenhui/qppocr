# 并发到底有没有用（2026-10-10）

结论先说：**进程级并发只值 +4.5%，而且第一次量出来的「零收益」是量在了一个
死旋钮上。** 所以「提高并发」这条路基本关掉了——GPU 在单图下单进程就已经
~95% 忙，瓶颈在**内核内部**，不在空闲时间。

## 0. 陷阱：`--workers` 对 `bench` 子命令**完全无效**

第一轮对比用 `bench --workers 1|2` 量，四组 img/s 全是 3.7~3.8，看着像
「并发没用」。查代码：

- `crates/qppocr-cli/src/main.rs:640 corpus_round()` —— 就是
  `for path in &o.images { engine.run(&img) }` 的**纯顺序循环**，从头到尾
  **没读过 `o.workers`**。
- `bench` 子命令自己的帮助文本就写着：「同进程跑完整语料（**不逐图起进程**）」。

⇒ `bench --workers N` 的 N 被完全忽略，四组量的是**同一个配置**。
真并发路径是**普通 CLI**：`auto_workers()`（main.rs:318/323，`N.min(图数)`）
→ `main.rs:559` 起子进程。

**这类「零收益」必须先查旋钮**，同类纪律见 memory
`ab-null-may-be-stale-binary`（开关没编进二进制时 Δ 恒为 0）。

## 1. 真路径的对照（49 张，medium，metal，奇偶交错）

```
workers=1  14.15 s  3.46 img/s
workers=2  13.52 s  3.63 img/s     Δ −4.5%
workers=1  14.64 s  3.35 img/s
workers=2  13.98 s  3.51 img/s     Δ −4.5%
```

两轮**符号与幅度都一致**（−4.5%），不是噪声。

## 2. 为什么只有 4.5%

第二张图只买到 4.5% ⇒ **单图单进程时 GPU 已经 ~95% 忙**。

这与「整图只有 33% 峰值算力」**不矛盾**：整图 308 GFLOP / 275.8 ms =
1117 GFLOPS。低的不是占用率，是**每个内核自己的算术强度**——
`n_conv8_mma` 已经贴在自证天花板 2209~2467 GFLOPS 的 87~98%（det 侧），
而 `n_conv_dw`、访存节点这些是**发射槽/访存路径**受限（memory
`activation-traffic-is-not-the-constraint`），加并发也填不进去。

**结论：加进程填不满，因为没空可填。**

## 3. ⚠️ 更正：「并发致瘸」是我转述错了自己的 memory（2026-10-10 改）

本节原先写「这台机器并发的 Metal 进程一多就把整条访存通路打到 1/70，
所以没试 workers=3」——**这个归因是错的，已更正。**

`metal-unbound-buffer-wedges-gpu` 自己做过三次自我更正，**最终定稿（2026-10-08
22:22，「以这条为准」）写的是：触发变量是「一个 session 里第几张图」，
总图数、进程数都不是变量。** 历史最小复现器是 **2 张图、1 个进程**（并发度
最低的一档）就卡死；真根因是我们自己的 `arena` bug
（[[metal-shared-arena-clobbers-plan-statics]]，**已修**，fixcheck 5/5）；
memory 原文专门叮嘱「**别再把因果说成『引擎打瘸了 GPU』**」。`--workers 0`
= 5 进程那条注脚也写着「这点值得记，但它**不是**致瘸变量」。

那份 memory 的 frontmatter 描述此前还留着被正文推翻的旧标题（「并发进程数
一多 → 访存掉 1/70」），我一并改掉了 —— 否则它会被反复当成活结论引用。

今天实测同向：`--workers 2` 跑 49 张 × 4 轮无卡死；`fixcheck.sh` 的 10 图一会话
（37 次缓存重放 = 当初的致瘸形态）① ② ④ 全过。

**所以「没试 workers=3」的理由是收益率，不是安全**（§2：2 个进程只买到 4.5%，
3 个约摸再 +1~2%）。安全上**没有**理由拦住它。

## 4. ⚠️ 更正：本机**没有**持久降级（上一版这里也是误判）

上一版写「blit 从 90~93 掉到 80.8，静置后仍 83.6，**持续 ~10% 降级**」。
2026-10-10 复测：连跑三次 `health.sh` = **91.18 / 91.40 / 88.70 GB/s**，健康带。

而且 83.4 那次并不构成异常证据：`health.sh` 自己的健康阈值就是 **≳83**，
memory 记录的健康读数历来在 **82.9 ~ 94.75** 之间（82.91 那次也是「健康」）。
正确模型是 **「一轮重负载后短暂下沉，随空闲恢复」**——那次静置 180 s 只回到
83.6，再往后（今天复测）回到 88.7~91.4。**不是持久降级。**

结论：绝对数字**建议在静置后采**，但不必把它当「机器坏了」；
配对交错的比较不受影响。

> 纪律：读 `health.sh` 的退出码**不要走管道**（`... | grep ...; echo $?` 取到的是
> `grep` 的退出码）——我今天在这里又踩了一次，`rc=0` 是假的。

`recoveryCount = 1` 是早先 `mm_sg_scan` 页故障的残留（**不重启不清零**）。
它曾被 `health.sh` 放在带宽之前**直接判死**，导致门禁**恒返回 2、彻底失效**；
已修（改成带宽为准、计数器只作提示）——这正是 memory 自己早就写下的那条
「为 0 不代表健康，以实测带宽为准」。

## 4.5 ⚠️ 顺带挖到的**真问题**：Metal 路径会静默吐错行（比性能重要）

见 `flake_2026-10-10.md`：单图 metal 跑 8 次有 **1 次**某行 `text=""`、`conf=0.0`；
同图 CPU **8/8 稳定**。这是正确性 bug，不是性能余量。

## 5. 如果还想榨并发：做**进程内**流水，别加进程

既然 2 个进程能拿 4.5%，同一份收益可以在**单进程内**拿到：让
`run_once` 不把 det→cls→rec 串死，而是**跨图流式**（det 图 k+1 与
rec 图 k 在同一个 `MTLCommandQueue` 上重叠）。这样避开了多进程那条
会打瘸的通路，用户拿到的还是那 4.5%。

但 4.5%（medium ~12 ms）值不值这个改动，得看还有没有别的更大的活。
目前账面上更大的仍是**任务 #39：同一个 `n_conv8_mma` 在 rec 比在 det
慢 26%，且同形状派发之间有实测 1.47× 的差**。
