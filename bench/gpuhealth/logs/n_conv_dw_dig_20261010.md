# 挖 `n_conv_dw` 的 9×9 —— 一条把探针结论钉在产线地板上的内核（2026-10-10）

任务 #33。`n_conv_dw` = **24.43 ms / 21 条，占 det 设备端 21%**，是全 det 第二大的
一笔；其中 **9×9 那批占 ~80%**，最大单条 `Conv.64`（c=256, m=51840, grid=12960）
**14.05 ms**。

**一句话**：这条内核在两轮、共 **11 个候选**之后仍然是死的。本轮最重要的产出
不是「找到了什么」，而是**证伪了一种方法论**——`p_dw_interior` 在孤立探针里
**1.14×**、位级一致、过 CPU 对拍，原样搬进生产却让 `Conv.64` **13.80 → 16.38 ms
（+19%）**，三轮交错复现。**生产内核一字未改。**

## 0. 本轮新增的探针（`probe_dw.metal`）

| 变体 | 干了什么 | 结果正确？ |
|---|---|---|
| `p_dw_interior` | 内点/边界双路径（内点走没有 compare 的循环体） | ✅ 位级一致 |
| `p_dw_incr` | 单层循环 + 增量 `ky/kx`（干掉 `t/kW` 倒数乘法序列） | ✅ |
| `p_dw_intun` | 内点路径 + `#pragma unroll 4` | ✅ |
| `p_dw_intinc` | 内点路径 + 增量 `ky/kx` | ✅ |
| `p_dw_tap1o3` / `p_dw_tap2o3` | 只跑 1/3、2/3 个 tap | ❌ 故意算错（尺子） |

跑法：`cargo test --release -p qppocr-metal conv_dw_variant_scan -- --nocapture`
（原始输出 `dw_scan_20261010.txt` / `dw_scan2_20261010.txt`）。

内点谓词只判**首尾两个 tap**（`ih = oh*sH + ky - padT` 对 `ky` 单调，故两端在界内
⟺ 全部在界内，与 stride 无关）。判宽了会把 `uint` 回绕成天文数字地址、直接把 GPU
打瘸，所以测试在**派发前**用同一算式在 CPU 上逐个输出位置暴力验过，不成立就 panic。
五个形状全过，内点占比 82.4%~97.7%。

## 1. 孤立探针里的读数（9×9 c256 136×240，m=32640）

| 变体 | ms | vs base |
|---|---|---|
| `p_dw_base` | 5.294 | 1.00× |
| `p_dw_interior` | 4.664 | **1.14×** |
| `p_dw_now`（去权重装载） | 5.034 | 1.05× |
| `p_dw_noin`（去输入装载） | 5.229 | 1.01× |
| `p_dw_win`（输入折进 1 KB 窗口） | 5.429 | 0.98× |
| `p_dw_nodiv`（嵌套 ky/kx 循环） | 7.202 | **0.74×** |
| `p_dw_u9`（全展开特化） | 7.383 | **0.72×** |
| `p_dw_wide4`（4 个通道块/线程） | 6.278 | **0.84×** |
| `p_dw_incr`（增量 ky/kx） | 7.093 | **0.75×** |
| `p_dw_intun`（内点 + unroll 4） | 8.971 | **0.59×** |
| `p_dw_intinc`（内点 + 增量） | 7.782 | **0.68×** |
| `p_dw_fma`（全去、只留 FMA） | 1.137 | 4.66× |
| `p_dw_nobc`（无 pad 配置，删边界判断） | 4.289 | 1.15× |

其它形状：内点 1.13×（68×120）、**1.17×**（9×9 c64）、1.03×（3×3 c128）、
1.12×（3×3 c512）。`incr` 在 9×9 **c64** 上是 **1.32×**（唯一一个正的结构改动），
但在 c256 上是 0.75× —— 不成立为处方，因为 c256 那批才是大头。

### 读法

**「结构改进」无一例外是负的**：嵌套循环、全展开、加宽每线程、增量计数器、
部分展开 —— 五条路，全部更慢，其中 `intun` **0.59×**。同时**削掉单项指令也
不值钱**（去输入装载 1.01×、去权重装载 1.05×）。而**全拿掉**是 4.66×。

⇒ 这条内核被**逐 tap 的地址依赖链**绑住，且它对**寄存器压力/取指**极其敏感：
任何让循环体变大、寄存器变多的改动都会被占用率下降吃掉。紧凑、寄存器最省的
单层循环体 + 最高占用率，**就是它的最优点**。

## 2. 时间对 **tap 条数** 近似线性

`tap1o3` / `tap2o3` 保持循环体逐字相同，只改迭代次数：

| taps | ms |
|---|---|
| 27 | 1.861 |
| 54 | 3.541 |
| 81 | 5.294 |

最小二乘：`t = 0.181 + 0.0622 · taps`（用 27/54 拟合，反推 81 → 5.221 vs 实测
5.294，**差 1.4%**）。**这是本轮唯一有正收益空间的信息**：想快就得**减 tap**。

注意 3×3 那档 `tap1o3` 只有 **1.07×** —— 因为 3×3 已经顶到 DRAM（下界 0.36 ms
vs base 0.366 ms = 91 GB/s，就是本机上限）。**减 tap 只对 9×9 有意义。**

## 3. ⚠️ 本轮的主产出：**孤立探针的胜势不迁移到生产**

`p_dw_interior` 看着是白捡的：孤立 +14%、位级一致、过对拍、不需要无 pad 配置。
把它**原样**搬进 `shaders/n_conv_dw.metal`（只改这一个文件，其余一字未动），
用**真计划**复核：

```
QPPOCR_GPU_KERNEL_PROF=400 ./qppocr bench img-001.jpg --device metal \
   --tier medium --preset balanced --rounds 1 --quiet --workers 1 --det-only
```

| | `Conv.64` | `n_conv_dw` 合计 |
|---|---|---|
| 旧内核 | **13.80 ms** | **24.16 ms** |
| 内点双路径 | **16.38 ms（+19%）** | **27.52 ms（+15%）** |

三轮**交错**复现（奇偶轮换，抵消次序效应）：

```
round1  new 26.32  old 24.14
round2  new 26.12  old 24.73
round3  new 26.19  old 24.65
```

**同一个改写：孤立探针 +14%，真内核 −16%。** 变量只有一个（那个 shader 文件），
所以归因是干净的。差别只剩**周围那份代码**：act/残差/写回的尾部、以及整个内核
一起过寄存器分配与取指 —— 循环体翻倍的代价盖过了分支的收益。

**已回退，生产内核一字未改。** 顺带试了同一思路的**最小**写法（把
`ih < 0 || ih >= inH` 两条有符号 compare 合成一条无符号 `(uint)ih >= inH`，
不复制循环体）：Δ = +1.19 / −0.01 / −2.29 ms，**平局**，也没有理由留。

### 教训（已写进 `probe_dw.metal` 头注释）

> 探针只能用来**划掉**候选（它说「没用」基本可信），不能用来**拍板**
> （它说「有用」不算数）。这条内核上的任何胜势都必须用**真计划**复核。

上轮 `n_conv8_mma` 的结论（权重免费、并行度死）是**否定式**的，不受这条影响；
本轮的正向结论恰好踩中了它。

## 4. ~~唯一还活着的路：分离式 9×1 + 1×9~~ —— **已证数学上不成立，作废**

> **2026-10-11 追记（本节作废）**：这条路的前提是「9×9 深度可分离核能拆成
> 9×1 与 1×9 两趟」。这不是工程难度问题，是**数学前提本身不成立**：拆分要求
> 核矩阵的秩为 1，而实测（`bench/gpuhealth/onnx_dw_sep.py`，对模型里每条 dw
> 权重做秩 - 1 可分离性检验）σ2/σ1 = **0.233 ~ 0.998** —— 没有一条接近秩 1。
> 那几条 0.99 的尤其致命：**看着像可分离，拆了就是错的**。
> 所以下面这套估算只作为「一次被前提打败的估算」保留，**不要再引用**。

原估算如下（保留存档）：

由 §2 的拟合，18 个 tap 的一趟 ≈ `0.181 + 18 × 0.0622 = 1.30 ms`
（136×240 那档；换成真 `Conv.64` 的 m 要 ×1.589 ≈ **2.07 ms/趟**）：

| | 估算 |
|---|---|
| 两趟计算 | 2 × 2.07 = 4.14 ms |
| 中间张量（53.1 MB 写 + 读）@ 91 GB/s | +1.17 ms |
| **合计** | **≈ 5.3 ms vs 实测 13.80 ms ⇒ ~2.6×** |

**但代价是硬的**：

1. **数值变了** —— 81 项按行主序累加，变成「先 9 项、再 9 项」两级求和。
   误差在 1e-7 量级，但不再是位级一致，`det_session_end_to_end` 那种
   `max|diff| = 6.7e-8` 的对拍口径要改。
2. 多一个中间张量、多一条 dispatch、plan 侧要改（`plan.rs` 的 dw 出口）。
3. 只有 9×9 值得（3×3 已经顶 DRAM；5×5 未测）。
4. **按 §3 的教训，这个 2.6× 也只是估算，必须用真计划复核。**

⇒ 用户此前明确要求「**先不影响精度的情况下去优化**」，所以**没有动手**。
要不要开这条路，需要用户拍板。

## 7. 第三轮：**瓦片暂存落地了**（2026-10-11，§3 的教训反向用对了一次）

§3 说「孤立探针的胜势不迁移到生产」，但那次的探针是**剥壳的**（把寄存器压力
/ 取指这些唯一相关的成本剥掉了）。这一轮的 `p_dw_tile` 是**逐字结构的复制**：
和 `n_conv_dw` 共用同一段尾部（bias / act / 残差 / 写回），只在数据来源上
把设备内存换成线程组内存。**这一类迁移了。**

### 7.1 生产读数（真计划逐内核剖析，medium det，196 条 dispatch）

| | 之前 | 之后 |
|---|---|---|
| dw 家族合计 | 17.27 ms | **11.77 ms** |
| 单条最贵的 Conv.64（9×9） | 8.56 ms | **5.198 ms（1.65×）** |
| 设备端合计 | 98.12 ms | **92.64 ms** |

`env_ab.sh 8 4 QPPOCR_METAL_DW_TILE=0`（medium，交错）：Δtotal 中位
**+6.65 ms**、Δdet **+4.95 ms**，符号 4/4 同向，A 臂漂移 1.07× 过门禁。
逐位性：tiny / small / medium 各 40 图 det 输出 **JSON 字节相等**
（`dw_tile_bitcheck.sh`，剥掉 `timing` 块）。

### 7.2 逐位为什么成立（比探针笔记更硬的证明）

累加次序一字未改（`t` 行主序 == `dy` 外层 / `dx` 内层），在界 tap 的乘数与
`n_conv_dw` 逐字同式；越界 tap 由 `continue` 变成加 `0.0*w`。而 `acc` 从
`+0.0` 起步，IEEE 加法只有「两个 `-0.0` 相加」才得 `-0.0` ⇒ `acc` 的取值域
里没有 `-0.0` ⇒ `acc + ±0.0 == acc` 恒成立。所以**严格逐位相同**，唯一的
破绽是 inf/NaN 权重（实际不存在）。完整证明在该 `.metal` 头注释。

### 7.3 试过并否掉的两条（同轮实测量，`logs/dw_tile2_scan_20261011.txt`）

| 形状 | base | **tile** | tilew | tile9 | fma |
|---|---|---|---|---|---|
| 9×9 c256 136×240 | 5.324 | **2.850 (1.87×)** | 2.772 (1.92×) | 5.858 (0.91×) | 1.120 (4.75×) |
| 9×9 c256 68×120 | 1.339 | **0.761 (1.76×)** | 0.771 (1.74×) | 1.566 (0.86×) | 0.294 (4.55×) |
| 9×9 c64 136×240 | 1.325 | **0.717 (1.85×)** | 0.703 (1.89×) | 1.479 (0.90×) | 0.292 (4.53×) |
| 3×3 c128 136×240 | 0.366 | 0.466 (0.78×) | 0.473 (0.77×) | — | 0.155 (2.36×) |
| 5×5 c64 4×32 (Conv.21) | 0.007 | 0.006 (1.12×) | 0.007 (0.96×) | — | 0.003 (2.35×) |
| 5×5 c128 2×32 (Conv.27) | 0.006 | 0.007 (0.78×) | 0.008 (0.71×) | — | 0.003 (1.95×) |

* **`p_dw_tilew`**（权重从设备内存直读，砍掉 `shW` 暂存）与 `p_dw_tile`
  统计上同一 ⇒ **权重暂存是免费的**，"权重免费"在这条内核上再证一次。
* **`p_dw_tile9`**（K=9 编译期常量 + 双循环全展开）**0.86~0.91×** —— 明显
  更慢，寄存器压力把收益吃光。又一次坐实本机那条经验：**凡是放大循环体的
  结构改动都输**（nodiv/u9/wide4/intun/tile9 五连败）。
* **5×5 两条只有 6~7 µs 绝对量**，掷硬币（1.12× / 0.78×）⇒ 生产门槛据此
  从 `5..=9` 收到 **`7..=9`**（见 `plan.rs` 的 `dw_tile` 与提交 `93f09e7`）。

### 7.4 这条内核剩下的余量在哪

瓦片版到 473 GFLOPS，而 `p_dw_fma`（把寻址和装载全砍掉）有 1207 GFLOPS ——
缺口是**每 FMA 一次 shared load**。要关掉得上 channel-major 的瓦片布局 +
寄存器分块，但按 7.3 那条五连败的经验，**在这台机器上加复杂度的期望是负的**，
判定：**不再挖**。

### 7.5 真正的建议

det 的账本已经合上，**逐条都量过、都不是假设**：

* dw 家族：本轮落地 −5.5 ms，剩下的余量被 shared-load 速率挡着（不可经济地关）；
* 纯访存那批（n_elem / n_concat_c / n_channel / n_resize / n_pool ≈ 9~10 ms）：
  实测 **84~101 GB/s vs 本机 95 GB/s 屋顶** ⇒ 已到；
* MMA 家族（~66 ms，det 的 71%）：按计划形状反算 **~1970~2160 GFLOPS**，
  贴着它自己实测的 2044~2444 天花板 ⇒ 已到。

⇒ **det 结构上没有剩的活口了。** 下一锄头要么挖 rec（但 rec 已被
[[rec-one-run-per-line-sets-a-2ms-floor]] 判定走完），要么换问题。
